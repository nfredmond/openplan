## Save and recovery behavior

The service validates the complete command and binds its actor, workspace and campaign to the caller's authenticated identity. The eventual route must supply that identity. It reads the exact saved request through the staff-authenticated client before consulting current history or evidence. Recovery requires the complete original intent and context bytes, so a correction or removal does not turn an old acknowledgement into a new write.

A new write requires complete verified history and the exact predecessor ID and hash. Linking or refreshing also requires the submitted context to pass the retained-evidence verifier and match current reviewed evidence. Withdrawal requires an active preceding link and preserves its context even after the response has been removed. The native service-only writer repeats authorization and currentness checks under its locks.

If the transport loses the acknowledgement after a write, the service reads the original request instead of submitting another write. It also attempts exact recovery after a native conflict or retryable lock result. An error-bearing RPC result never becomes success merely because it contains data. The returned receipt must match the complete command and extend the previously verified history before the service acknowledges it.

Database and integrity failures use bounded error categories. A valid record for another command is a conflict; corrupt retained evidence remains unavailable. A test demonstrated that checking scope before nested integrity incorrectly classified corrupt evidence as a conflict. The reader now validates the retained context against its own recorded scope before comparing it with the requested scope.
