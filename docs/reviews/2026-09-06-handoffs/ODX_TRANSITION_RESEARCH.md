# ODX transition and WaypointMap workflow research

Research date: September 6, 2026. OpenPlan source inspected at `2614293b0b1be8d8694433f9612834c3d7dd5b72` in the isolated handoff checkout. This is a documentary and source-code assessment. No processing engine, container image or imagery dataset was installed or run. No services or historical aerial records were changed.

## Decision

Evaluate ODX/NodeODX as the preferred candidate for upgrading OpenPlan's photogrammetry processing, with a measured transition gate. Do not replace all drone functionality merely by changing the Docker image. ODX is a separately maintained fork with real newer implementation work. Its speed advantage is plausible and includes specific upstream stage-level claims, but whole-job speed, output quality and recovery on Nathaniel's computer remain unproved.

This extends the existing [reuse decision](../2026-09-04-pre-handoff/AERIAL_REUSE_AND_IMPLEMENTATION_DECISION.md), [21-family benchmark](../2026-09-04-pre-handoff/ODM_WEBODM_FEATURE_BENCHMARK.md) and [current capability review](../2026-09-04-pre-handoff/AERIAL_CURRENT_CAPABILITY_REVIEW.md). They already called for a NodeODX trial. Place the explicit benchmark and migration decision inside [roadmap M5b.2](../../ROADMAP.md), with QC/features in M5b.3–4 and operating acceptance in M5b.5. Keep the current OWP work as the primary outcome.

## What is newer, and what is actually faster?

WebODM announced its separation from OpenDroneMap on April 6, 2026 and named ODX and NodeODX as its maintained forks. ODX is therefore a newer branch of the same broad engine lineage, not a renamed official ODM release. ODM also continues to receive commits. Neither version numbering nor the separation announcement proves comparative quality. [First-party announcement](https://webodm.org/blog/announcement/)

There are concrete reasons to benchmark ODX:

- ODX 3.8 introduced the newer OpenSfM integration and GPU Hamming matching. Its current adapter chooses Hamming automatically when it detects a GPU and has at least 32 photos. The source explicitly avoids this automatic choice for smaller sets because training overhead can make it slower. ODM's inspected adapter supports CPU matching modes and a different GPU SIFT extraction path. Therefore "both support GPU" conceals a material difference. [ODX integration change](https://github.com/WebODM/ODX/pull/27), [pinned ODX matcher selection](https://github.com/WebODM/ODX/blob/eb9fd56ac430fc3735401d88aaef9945ebd00e14/opendm/osfm.py#L283-L314), [pinned ODM matching/extraction](https://github.com/OpenDroneMap/ODM/blob/69ca6212ca2f885b41cee6bb19d32f6ddecf79bc/opendm/osfm.py)
- ODX 3.8.2 reports approximately 50% less memory and 20% less runtime in the point-filtering stage. The linked change supplies no reproducible full-workload table, hardware description or independent quality comparison. These percentages must remain upstream claims about that stage. [Change #33](https://github.com/WebODM/ODX/pull/33), [release 3.8.2](https://github.com/WebODM/ODX/releases/tag/v3.8.2)
- Parallel orthophoto block merging is a real merged change. It is relevant to large split/merge jobs; it supplies no whole-job speed factor for OpenPlan. [Change #24](https://github.com/WebODM/ODX/pull/24)
- The 6x number in ODX 3.7.0 concerns building the software. It is not six times faster drone-image processing. [Release 3.7.0](https://github.com/WebODM/ODX/releases/tag/v3.7.0)

The searched project READMEs, releases, linked implementation changes and documentation did not establish a reproducible ODM-versus-ODX end-to-end benchmark with matched settings and independently checked outputs. No numeric OpenPlan speedup is justified yet. The newer OpenSfM repository includes a benchmark runner; its existence is useful for attribution of stage changes, not a published result. [OpenSfM benchmark documentation](https://github.com/WebODM/OpenSfM/blob/4fa900ba4f546aec5ab92001bde1acf6e5b33f85/doc/benchmark.md)

## The actual OpenPlan transition

The present [compose file](../../../workers/odm_worker/docker-compose.yml) uses mutable `opendronemap/nodeodm`, with neither a GPU declaration nor durable engine/worker data mounts. The [worker](../../../workers/odm_worker/main.py) keeps jobs, its queue and artifact registrations in memory. Its result benchmark writes `engine: nodeodm`, elapsed seconds, preset and image count, with no exact engine version. Its three presets do not explicitly choose matcher type. A simple endpoint/image replacement would therefore change effective defaults without adequate historical identity and would leave restart defects in place.

The [client](../../../workers/odm_worker/nodeodm_client.py) uses `/info`, task init/upload/commit/info and `all.zip`. NodeODX documents those API paths and retains familiar raster/cloud archive paths. Its default archive also contains georeferencing, textured models, reports, camera metadata and optional tiles. This makes extension of the existing adapter a sensible approach. Source compatibility is not runtime acceptance. [Pinned NodeODX API](https://github.com/WebODM/NodeODX/blob/a480583ff8a4d7aaa23f890433b78727ebe750d0/docs/index.adoc), [archive construction](https://github.com/WebODM/NodeODX/blob/a480583ff8a4d7aaa23f890433b78727ebe750d0/libs/Task.js#L444-L462)

OpenPlan currently stages only an orthophoto, derived PNG preview, DSM, DTM and LAZ. It discards useful meshes and quality reports even though the [shared contract](../../../openplan/src/lib/aerial/processing-contract.ts) already names a mesh artifact. Extend the output manifest, custody and viewers deliberately; requesting richer output without retaining its bytes is not delivery. Version any expanded contract compatibly with the external Aerial Intel worker, which also consumes it.

Compatibility checks must include differences that can silently change results. ODX changes default matcher selection and matching graph rounds; its configuration maps the deprecated planar SfM choice to incremental. The inspected ODX option set removes ODM's `build-overviews`, `merge-skip-blending` and `pc-rectify`; `cog` replaces the first, while the others require explicit capability mapping or refusal. NodeODX can automatically add `pc-ept`, `cog` and `gltf` when supported. Record effective options after API additions, not only OpenPlan's requested preset. [ODX configuration](https://github.com/WebODM/ODX/blob/eb9fd56ac430fc3735401d88aaef9945ebd00e14/opendm/config.py), [NodeODX postprocessing options](https://github.com/WebODM/NodeODX/blob/a480583ff8a4d7aaa23f890433b78727ebe750d0/libs/Task.js#L120-L146)

Keep original photos, controls, previous runs, selected map layers, held artifacts and frozen report/grant evidence. New processing creates a distinct run with exact engine/API/image digest, source hashes, effective settings and output manifest. Retain ODM as a selectable compatibility/reproduction backend until each claimed workload has passed its transition gate. Never silently retry an ODX failure under another engine or overwrite an approved prior result.

Read-only checks found an RTX 4070 Ti SUPER with 16,376 MiB VRAM and driver 595.84, 24 logical processors, 31 GiB RAM and approximately 400 GiB disk available. ## Benchmark and transition acceptance

This is the proposed acceptance procedure inside M5b, not a second roadmap or a completed test:

1. Freeze permitted imagery, sensor metadata, controls/check roles, intended products, horizontal and vertical reference, output resolution and use-specific accuracy/completeness criteria before inspecting comparative results. Cover a small RGB set below 32 images, a representative larger corridor/site set, terrain/vegetation, controlled/checkpoint imagery and each spectral/oblique/split workload claimed in the migration. Public sample data can establish mechanics; missing independent survey control leaves accuracy unproved.
2. Pin a tested ODM/NodeODM pair and ODX/NodeODX pair by image digest and source. Capture `/info`, supported options, effective options, CPU/GPU/driver, RAM/disk limits and the exact OpenPlan worker/contract. Run a matched explicit-settings comparison and a separately labeled normal-defaults comparison. Do not equate preset labels with equal algorithms or remove difficult photos for one engine.
3. Repeat complete jobs at least three times where feasible, counterbalancing engine order and identifying cache state. Report each run and failure, whole-job time from upload through retained artifacts, stage times, peak RAM/VRAM/scratch storage and operator correction time. Protect other active services through explicit resource admission. Faster stages that worsen full completion time or output quality do not justify a blanket migration.
4. Independently inspect/reopen GeoTIFFs, clouds, meshes, QA reports and tiles. Compare reconstructed-image coverage, holes/seams, geometry/units, checkpoint residuals, calibration and full-resolution quantities against the frozen criteria. Preserve disagreements and failed use cases; numerical equivalence or a universal accuracy percentage is not assumed.
5. On isolated services, interrupt upload, committed processing, completed-but-uncollected outputs, callbacks and custody. Prove reconciliation, duplicate retry, cancellation, expired links, failed DB writes, oversized archives, disk/GPU exhaustion, CPU operation and unsupported settings. Exercise restore and rollback while retaining historical source and result identity. Changing engines cannot stand in for making OpenPlan's worker durable.
6. Trace every existing aerial and downstream workflow through the new run: intake, processing, map layers, reports/grants/evidence export, permissions, sharing, independent file reuse and installation. Require desktop, 390px and keyboard journeys, live cross-tenant checks, stored-record inspection and harmless/targeted mutations for changed guards. Keep controller/USB acceptance separately visible in M5b.1.
7. Select ODX as default only for workload profiles with complete outputs, use-specific quality acceptance and recovered-job evidence, plus a demonstrated speed/resource or other documented user benefit without material regressions. Other profiles retain ODM or a truthful unsupported state. Broad replacement requires coverage of every existing claimed profile; a successful RGB demonstration cannot close all 21 families. Practitioner usefulness and survey/finance consequences still need the relevant people.

Suggested canonical-roadmap addition: "September 6 ODX assessment makes ODX/NodeODX the preferred engine-upgrade candidate within M5b.2. Benchmark pinned engines on matched permitted datasets, exact effective settings, complete outputs, independent quality and recovered jobs before changing defaults. Track GPU matching and resource gains, independent checkpoints and unit-aware QA, and sensor-specific improvements in M5b.3/5. Preserve all existing mission, controller and evidence obligations; retain ODM compatibility until each profile passes. M5b.4 keeps the documented splat training export/external-training/import/display workflow, with optional integrated local training subject to separate evidence. No blanket speed or capability claim follows from the fork name."

## WaypointMap as Nathaniel's mission-planning reference

Nathaniel identified WaypointMap on September 6 as the tool he actually uses to create routes/waypoints with many variables and upload them to a connected DJI controller. That is direct evidence of the workflow OpenPlan needs to match. It does not identify his aircraft, controller, computer/browser path or firmware. Keep those fields open until his actual combination is observed; do not assume that an enterprise Pilot 2 profile covers it.

WaypointMap is a separate capture-planning application. ODX reconstructs imagery after capture. Both fit the existing Aerial module, with WaypointMap informing M5b.1 and ODX informing M5b.2–5. No replacement module is needed.

### Published controls and compatibility

The official tutorial describes drawing a shape, generating points, dragging/editing points, adding points with a marker, stacking selections and downloading a DJI KMZ. Its homepage also promotes point-of-interest planning. These provide concrete reference tasks for the existing OpenPlan AOI/grid/editor, rather than a reason to build another route editor. [Tutorial](https://www.waypointmap.com/Home/Tutorial), [homepage](https://www.waypointmap.com/)

The Air 3S page identifies altitude, speed, gimbal angle and flight-line spacing as basic controls. Its advanced controls include terrain-dependent altitude adjustment, per-waypoint actions, reversed order, pass orientation, straightened paths, DJI Fly KMZ import/edit, dense waypoint generation, overlap/photo interval and a KMZ installer. These are vendor-described controls; no editor or mission file was exercised here. The terrain claim does not establish the elevation source, terrain resolution, obstacle coverage or guaranteed above-ground clearance. OpenPlan must retain those sources and limitations instead of copying the marketing promise. [Air 3S controls](https://www.waypointmap.com/drone/dji-air-3s-automated-mission-flight-planning)

The vendor's supported-aircraft page names DJI Lito X1, Mini 5 Pro, Mavic 4 Pro, Mini 4 Pro, Air 3/3S and Mavic 3/3 Pro/3 Classic, and requires built-in waypoint capability. The tutorial lists RC-N1/N2/N3, RC and RC 2/RC Pro/RC Pro 2 paths. Every claimed pairing/firmware/OS still needs testing. No new camera, LiDAR or endurance claims from model-specific marketing pages are adopted. [Supported aircraft](https://www.waypointmap.com/Home/SupportedDrones), [controller-specific tutorial](https://www.waypointmap.com/Home/Tutorial)

### How the documented transfer actually works

The tutorial requires an existing DJI waypoint mission. Its USB path connects the controller, accesses DJI Fly's waypoint folder and replaces an existing KMZ with the renamed generated file. Separate microSD/iPhone/Android paths have different access limits; Mac guidance names OpenMTP. Linux acceptance is not established. This is third-party stored-mission replacement, not Pilot 2's import menu or a universal DJI upload API. [Official WaypointMap tutorial](https://www.waypointmap.com/Home/Tutorial)

WaypointMap advertises an automatic mission installer, including one-click RC 2/Pro transfer on the Air 3S page. This review did not establish the installer's executable, supported operating systems, protocol, browser permissions, backup behavior or disconnected operation. Nathaniel's experience establishes usefulness on his setup; the site's feature list does not settle the mechanism. The editor redirects an unauthenticated visitor to login, and no account or controller session was opened. [Installer description](https://www.waypointmap.com/drone/dji-air-3s-automated-mission-flight-planning), [editor entry](https://www.waypointmap.com/Home/Editor)

This changes how the [September 5 DJI report](../2026-09-04-pre-handoff/DJI_MISSION_EXPORT_USB_RESEARCH.md) should guide implementation. DJI's current help still says Fly does not support KML route import. It also distinguishes saving to the app from pressing GO, which uploads the route and starts the execution sequence. Controller-installation acceptance must stop before that action. [Current DJI Fly help](https://repair.dji.com/help/content?customId=01700007343&documentType=&lang=en&paperDocType=ARTICLE&re=US&spaceId=17) Its recommendation to avoid basing v1 on stored-mission replacement needs reassessment against Nathaniel's now-explicit reference.
