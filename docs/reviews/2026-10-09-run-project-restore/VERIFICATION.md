# Preserve project scope through ordinary database restore

The nonempty recovery fixture in PR 177 fails default `pg_restore` at `model_runs_project_workspace_match`. Its CHECK function reads `projects` before that table's data loads. PostgreSQL documents this limitation and recommends relational constraints for cross-table integrity. See the [PostgreSQL 17 constraints reference](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS) and [pg_dump ordering](https://www.postgresql.org/docs/17/app-pgdump.html).

Migration 27 adds a unique project identity/workspace pair and validated composite foreign keys for `runs`, `model_runs`, `county_runs` and `stage_gate_decisions`. These are all four constraints that call `run_project_matches_workspace`. The replacement keys validate existing records before any old CHECK is removed, within one transaction. Existing single-column foreign keys remain. Null project attribution remains valid. Project deletion still clears only the three run tables' project IDs and preserves their workspaces; stage-gate decisions retain their existing database cascade behavior. Application deletion refusals remain separate. Moving a referenced project into another workspace is now refused at the parent relationship as well.

The existing partial project indexes in each child support relationship lookup. The project pair adds one unique index. No row is backfilled, deleted or silently corrected. No grants, policies, scientific results or geography support change. The installed project-read policy is workspace-membership based, matching this scope boundary. The migration takes table locks and belongs in a maintenance window. It is applied only to owned proof databases during this work.

The native rollback suite passes baseline, harmless-comment and restored cases. It checks all four child workspace refusals, checks the named foreign-key diagnostics, refuses a parent workspace move, and verifies the deletion distinction. Removing the model-run composite key makes its cross-workspace update succeed and fails the proof. A separate fixture creates parent drift allowed by the old child-only CHECK; validation then refuses the upgrade and the transaction leaves no replacement index or fixture. These are database-owner integrity checks, not an end-user authorization campaign.

The dump/restore proof starts with the original failing archive. Default restore fails for the original constraint and a new connection confirms that its transaction left no application table. The known project-first workaround loads an isolated source solely so it can be upgraded. After migrations 24 through 27, a fresh custom-format dump restores through ordinary `pg_restore --single-transaction --exit-on-error`, with no custom list and no disabled constraints. All 966 rows across 340 application, Auth and Storage tables match by sorted JSON row counts and MD5. This checks ordinary corruption, not adversarial hash collisions; extension-owned records are excluded. All four new keys remain validated with matching definitions. The integrity controls also pass on the restored target and roll back without changing the compared records.

Forty-seven focused tests pass across the historical project-scope migrations, destructive-migration guard and combined inventory. The retained runners and JSON results identify the migration and assertion hashes. Dump files and fixture databases remain private local evidence. This is one nonempty source archive and native relationship verification. It does not establish every cross-table CHECK's restorability, every RLS policy, concurrent production cutover, Storage byte restoration or whole-installation recovery. Full CI and the parent integration acceptance remain required.
