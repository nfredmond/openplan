## SCI-01. Tokenless ActivitySim HTTP worker permits command execution and deletion

1. **Severity: High. Confidence: high.** The actual route executes a caller-selected command and deletes caller-selected synthetic files. External network reachability was not tested.
2. **Affected commits and locations.** Both commits named above. `workers/activitysim_worker/main.py:50-65` accepts executable templates, output paths and force; `main.py:105-113` skips authentication when the token is absent; `runtime.py:529-548` resolves the supplied output directory and recursively removes it; `runtime.py:581-588` prepares that directory before validating the bundle; `runtime.py:758-759,794-800` executes the supplied command. `Dockerfile:15` binds Gunicorn to all interfaces. `DEPLOY.md:16-20,134-141` calls the token optional and documents an exposed Docker port.
3. **Trigger and preconditions.** Run the shipped manual HTTP wrapper without `OPENPLAN_ACTIVITYSIM_WORKER_TOKEN`, with a reachable port. Caller knows an existing bundle directory. A usable configuration allows the executable path; a directory containing `manifest.json` is enough to reach directory preparation. The worker must have permission over the target files.
4. **Expected versus observed.** A remote request without authorization must not reach execution or filesystem replacement. An in-process request with synthetic peer address `198.51.100.27`, no Authorization header and no configured token returns HTTP 200. It removes `synthetic-record.txt` from an unrelated directory and runs a Python command that creates a harmless marker. The response reports `succeeded`.
5. **Consequence.** Anyone reaching this tokenless worker can run commands with worker privileges or destroy files it can modify. No host compromise, external attack or deployed exposure is claimed. The normal `npm run worker:activitysim` polling entrypoint is separate from this HTTP wrapper.
6. **Reproduction.** Run `evidence/science-venv/bin/python -B evidence/science-activitysim-http.py` from this report directory. The script imports the real Flask route and runtime, creates only temporary synthetic files, and records the result in `evidence/science-activitysim-http-result.json`. A configured-token request returns 401 and leaves files intact. The no-op comment mutation preserves the reproduction. Forcing the authorization branch changes the result to 401, caught by the HTTP-result assertion. No listener opens.
7. **Why existing checks miss it.** The 14 `workers/activitysim_worker/tests/test_runtime.py` cases run successfully in this review, but test the runtime directly. They do not test the HTTP authorization boundary or all-interface tokenless startup. Push CI's Python worker job covers `workers/aequilibrae_worker/test_*.py`, not ActivitySim's HTTP wrapper. The optional local worker runner does not substitute for a missing authorization test.
8. **Smallest plausible correction.** Refuse tokenless network operation and require authorization before runtime setup. Mirror or strengthen the existing county-worker fail-closed boundary. Make output roots and executables operator-owned configuration for HTTP use. Refuse `force` replacement outside an explicitly owned runtime directory, including symlink and ancestor cases.
9. **Regression check.** Exercise real HTTP routes with a remote peer, missing/wrong/correct token, valid synthetic bundle, arbitrary output directory and harmless command marker. Assert both response and absence of filesystem/process side effects. Test Gunicorn startup independently from `__main__`. Retain the no-op control and a removed-authentication counterexample.
10. **Release classification.** Shipped, documented optional runtime wrapper. Its name contains "prototype," but it is distributed with a Docker deployment command and actual execution behavior. This is not a new gap in the unfinished synthesis feature. Setting a token prevents this unauthenticated trigger; the unbounded filesystem trust remains an architectural concern for authorized callers.

## SEC-01. Encoded parent segments escape the approved Storage target

1. **Severity and confidence.** High severity. High confidence in the helper and SDK target escape, demonstrated with executable synthetic evidence. Moderate confidence in the complete unauthorized download chain because native route/database/Storage execution was not performed.
2. **Affected commit and locations.** Baseline `891a0d89a848133d44b9e4f314a76a922cd71ace`. `openplan/src/lib/models/artifact-source.ts:51–60` compares the raw bucket and prefix and rejects literal `..` only. `openplan/src/lib/files/tenant-scoped-storage.ts:19–29` delegates to it. `openplan/src/app/api/models/[modelId]/runs/[modelRunId]/artifacts/[artifactId]/download/route.ts:113–146` resolves the member-writable reference and passes it to the service-role signer. The same guard protects direct downloads at `artifact-source.ts:81–89`. Native SDK implementation was inspected in installed `@supabase/storage-js/src/packages/StorageFileApi.ts:709–725`, `905–916` and `1495–1497`; dependency behavior is recorded in the evidence, not treated as a repository source change.
3. **Trigger and preconditions.** An authenticated workspace writer controls a model-run artifact `file_url`, uses the approved bucket and their own run prefix, and supplies encoded parent segments after that prefix. A consequential foreign-object read also requires a known target bucket/path, an existing target and the normal configured service-role Storage client. UUID/path discovery was not demonstrated.
4. **Expected versus observed.** The guard should refuse a path whose effective request target leaves the authorized bucket or run. The actual guard accepts the encoded variant. The actual installed SDK prepares a request whose native `Request` path points to the other bucket after normalization. The control using literal parent segments is refused; the legitimate same-run object is accepted.
5. **Consequence.** The service role can be asked to sign a target different from the target the application authorized. This creates a credible cross-workspace artifact-disclosure path. It is not evidence that a foreign object exists, that its path is discoverable, or that native Storage returned its bytes. Ordinary model artifacts are sufficient for the source-level path; this finding does not depend on mutating frozen scientific evidence.
6. **Reproduction and direct evidence.** `evidence/security-storage-traversal.cjs` transpiles the exact helper source without editing it, uses the installed SDK, and captures the normalized URL with a synthetic fetch implementation. `evidence/security-storage-traversal.json` records all results. The execution sent no network request and used only synthetic strings. The sample begins with the approved `run-artifacts` bucket and own model-run prefix, yet the captured request path is `/storage/v1/object/sign/kb-documents/foreign/file.pdf`. The original schema permits a writer's artifact rows through owning-run membership at `20260318000026_model_run_stages_and_artifacts.sql:96–105,136–145`; `20260728000007_workspace_write_role_gate_children.sql:43` adds a writer gate, not target-path validation. The route itself documents member control at lines 113–115. Later scientific custody triggers inspected protect specified retained validation relationships; this review found no general URL-normalization guard replacing the shared helper.
7. **Why existing checks miss it.** `model-run-volumes-artifact-source.test.ts:138–151` checks an explicitly different bucket and an explicitly different run. `model-run-artifact-download-route.test.ts:11,125–130` mocks `createSignedUrl`, so its oracle does not normalize the URL as the installed SDK/network layer does. These checks can reject obvious strings while never examining the effective request target. No claim is made that every repository test was executed or searched exhaustively.
8. **Smallest plausible correction.** Make the shared guard reject noncanonical object-path segments before any privileged read or sign. Compare the canonical request target with the authorized bucket and prefix, or use a strict path alphabet consistent with generated object names. Review percent encodings, separator variants and URL delimiters together. Avoid a decoder that approves one representation while a downstream layer decodes again. No correction was applied.
9. **Regression and mutation evidence.** Add a focused helper/SDK test that checks the effective URL, retains ordinary filenames, and refuses encoded traversal. A native regression should establish permitted same-run access and denied foreign-bucket, foreign-run and revoked-user requests using disposable synthetic objects. Existing synthetic evidence demonstrates a harmless comment control producing identical results. An in-memory candidate that also rejects `%` changes only the unsafe case to refusal; reverting that condition reproduces the exact failed safety expectation. This is a diagnostic candidate, not a proposed complete production implementation. The evidence's process exit indicates the reproduction assertions succeeded, not that application security passed.
10. **Release status.** Released-code path at the recorded baseline. Independent helper/SDK defect, not unfinished synthesis context-history work. No development correction was independently verified in this subreview.

## PROV-01. Financial routes accept writes outside the approved action payload

1. **Severity and confidence.** High severity. High confidence in the demonstrated route defect. The reproduction runs the real handler and approval verifier with mocked access and database operations. Native row-level security was not part of this reproduction.
2. **Affected commit and locations.** Baseline `891a0d89a848133d44b9e4f314a76a922cd71ace`. `openplan/src/app/api/projects/[projectId]/funding-profile/route.ts:76-97,120-125`; `openplan/src/lib/runtime/action-registry.ts:100-119`; `openplan/src/lib/assistant/action-approval-server.ts:280-409`. The registered action omits amount authority, while the route accepts amounts in its broader manual PATCH schema.
3. **Trigger and preconditions.** An authenticated workspace writer has an unconsumed, unexpired `create_project_funding_profile` approval for the correct project and notes. Submit the same source/hash/approval headers and approved notes, adding `fundingNeedAmount: 9999999` and `localMatchNeedAmount: 7777777`. This requires the already-authorized writer's session. It does not establish cross-tenant access or an unauthenticated privilege escalation.
4. **Expected and observed.** The route should reject financial fields outside the approved action, or bind them to explicit consent if the action is deliberately broadened. Instead, the route hashes only kind, project ID and notes, consumes the matching approval, submits both changed amounts to its upsert and returns HTTP 200. Changing the signed note returns 403 before consumption or upsert, proving the real hash protection was reached.
5. **Consequence.** A stored execution can claim exact Planner Agent approval while changing financial fields the approval never represented. The normal registry sends null amounts, so this finding is about route enforcement under altered requests, not a claim that the normal UI automatically chooses those injected values.
6. **Reproduction and evidence.** Run from the review root:

   ```sh
   openplan/node_modules/.bin/vitest run --config docs/reviews/2026-10-01-independent-code-review/evidence/providers-approval.vitest.config.ts
   ```

   `evidence/providers-approval.test.ts` supplies four observations: unchanged approved payload accepted, harmless JSON key ordering accepted, changed signed note rejected, unsigned amount changes accepted. `evidence/providers-approval-output.txt` records the combined six-test run with the native recovery reproduction. It does not claim a live financial write.
7. **Why checks miss it.** `openplan/src/test/project-funding-profile-route.test.ts:90-116` tests a manual PATCH without approval headers. `action-approval-server.test.ts` exercises hashes presented to the verifier, not whether every persisted route field reached that hash. A correct verifier cannot identify an omitted field it never receives. Four existing relevant suites still passed 126 tests alongside this defect. The current browser registry also cannot demonstrate a hostile addition because it emits fixed null amounts.
8. **Smallest plausible correction and regression.** For Planner Agent requests, reject every mutable field outside the narrow approved action or reconstruct the write entirely from that action. Keep manual financial editing explicit. Add actual-handler tests that append each manual-only field to a valid approved request and assert refusal before consumption/write. Preserve unchanged payload and manual-edit controls. Do not merely broaden the hash schema without deciding whether the agent should have financial authority.
9. **Released/prototype/backlog.** Released route behavior, independent of unfinished context-history work. This differs from known KL-2026-09-04-046, which records non-atomic approval/effect/audit and delegated-authorship gaps. Exact approved-field binding is separately defective here.
10. **Cross-review and related locations.** The coordinating reviewer independently confirmed the omitted fields. Source inspection finds the same class in `funding-opportunities/route.ts:368-382,411-437`, which hashes title/project/program but persists additional financial and decision fields; `funding-opportunities/[opportunityId]/route.ts:130-169,179-182`, which hashes only the decision while updating other supplied fields; and `invoicing/invoices/[invoiceId]/route.ts:161-172,192-208`, which hashes the award link but can update invoice status in the same request. These related routes are source-established and were not all reproduced with the real verifier. Consolidate them as one audit of action-to-write binding rather than separate counts.

The profile route also uses upsert on project ID. An old create proposal can overwrite a profile created after proposal preparation, including nulling its amounts through the normal registry. The route has no create-only or expected-version predicate. This source-established stale-proposal consequence needs a separate concurrent database reproduction before grading actual lost financial history.

## SCI-02. County cancellation leaves descendants running and can hold the queue

1. **Severity: High. Confidence: high for surviving descendants and blocked cancellation; medium for an indefinite real modeling job.** The synthetic child survives cancellation and completes its write. An indefinite child was not left running.
2. **Affected commits and locations.** Both commits named above. `workers/county_onramp_worker/main.py:404-421` starts the bootstrap without a separate process group, signals only its PID, then waits without a timeout. `scripts/modeling/bootstrap_county_validation_onramp.py:72-74` launches child commands with `subprocess.run`. Those children inherit the bootstrap's captured output pipes. `docs/ops/KNOWN_ISSUES.md:219` describes cancellation and queue release as corrected under KI-2026-08-24-008.
3. **Trigger and preconditions.** Cancel a running county job while the bootstrap waits for a child process. The child retains inherited stdout or stderr. The default worker has one execution slot.
4. **Expected versus observed.** Cancellation should terminate the owned execution tree and release its slot, or report explicitly that termination remains unresolved. Actual `_run_job` kills the synthetic bootstrap while its child continues. The child writes a marker roughly 1.5 seconds after cancellation. The worker waits for that child before reporting `cancelled`, despite a 0.10-second test grace period. The no-op reproduction behaves the same.
5. **Consequence.** Cancelled work continues computing and writing artifacts. A child that does not exit keeps a pipe open, so the unbounded `communicate()` also keeps the worker slot occupied. The latter conclusion follows from the exercised wait and the missing timeout, rather than an indefinitely running test. No stale callback or cross-attempt artifact overwrite was demonstrated.
6. **Reproduction.** `evidence/science-repro.py` runs actual `_run_job`, replacing only command construction and callback delivery with synthetic owned resources. The parent script uses `subprocess.run` to launch a child that sleeps 1.5 seconds and writes a marker. The review sets the cancel event after child readiness. `science-repro-result.json` records surviving child output, elapsed cancellation time, final status and callback states. A comment-only function copy preserves behavior. Removing the cancel branch produces `completed`; the explicit `cancelled` assertion rejects that counterexample. All synthetic processes exit naturally.
7. **Why existing checks miss it.** The county worker's 10 tests return OK. Its queue-cancellation test uses `FakeProcess` at `tests/test_main.py:225-249`; `terminate()` flips a boolean and `communicate()` immediately returns. There are no children or inherited file descriptors, so that test cannot detect this defect.
8. **Smallest plausible correction.** Start each owned bootstrap in an isolated execution group and terminate its owned descendants, with bounded escalation and confirmed completion. Container execution needs its own owned-container termination semantics; killing the Docker client alone is not proof of stopping its container. Keep attempt identity and unrelated processes protected.
9. **Regression check.** Use a real parent-child process with inherited pipes, assert the child's delayed marker never appears, confirm the second queued job starts, and separately exercise a child that ignores the first termination signal. Include an unrelated control process that remains alive. Remove descendant termination to prove the test detects the defect. A VM/container power-loss drill remains separate.
10. **Release classification.** Released cancellation behavior, with a current known-issue entry claiming the earlier queue problem corrected. This finding narrows that correction's evidence. It is separate from the already listed in-memory ODM recovery risk and long-stage reaper concern.

## PROV-02. A rejected native answer blocks later connector jobs, including after cancellation

1. **Severity and confidence.** Medium severity. High confidence in the demonstrated recovery behavior. Production connector and native route are composed together; database and native provider generation are synthetic.
2. **Affected commit and locations.** Baseline `891a0d89a848133d44b9e4f314a76a922cd71ace`. `workers/planner_agent_connector/connector-worker.mjs:64-74,113-136`; `openplan/src/app/api/assistant/providers/native/route.ts:42-63`; `workers/planner_agent_connector/connector.mjs:77-87`; `openplan/src/lib/assistant/provider-project-task.ts:43-58`.
3. **Trigger and preconditions.** A native provider returns a completed answer that passes the connector's identity/string/byte checks but fails the application's output parser. The synthetic answer is valid JSON with the correct citation, `submittal: null`, and whitespace-only `answer`. This needs no oversized or malformed transport. The app rejects the trimmed empty answer. Actual provider frequency was not measured.
4. **Expected and observed.** Preserve the exact observed output and allow the attempt to reach a terminal rejection or cancellation, without generating again. The route instead returns 400 before the finish RPC. The connector has already synced a `completed` journal and reconciles terminal status only after HTTP 409. Recovery repeatedly resends the same invalid answer. Even after the database state becomes `cancelled`, the route parses the answer before reaching its finish RPC and again returns 400. Continuous mode labels this `connection_unavailable` and loops.
5. **Consequence.** One rejected result prevents all subsequent claims on that personal connection. Restart and ordinary cancellation do not clear the journal. The model is not called again, so this finding is blocked progress and misleading recovery guidance, not duplicate provider spending. Creating a new connection/directory is a workaround, with original evidence retained separately.
6. **Reproduction and evidence.** `evidence/providers-native-recovery.test.ts` runs actual `connectorCycle` and actual native `POST`. Its valid control records one claim, one generation and one successful finish. The rejected-answer case records statuses `[400,400,400]`, one claim, one generation, zero finish RPCs and journal phase `completed`. The last two cycles occur after the synthetic database returns cancelled state. Run with the same command as PROV-01.
7. **Why checks miss it.** `workers/planner_agent_connector/test/connector-worker.test.mjs:24-34` stubs every finish as success/failure without running the application's output parser. Its fixture answer lacks fields the real parser requires. Native route/parser tests and connector tests exercise their own boundaries separately. The connector's existing cancellation recovery probes return 409, which is the one code its recovery branch handles. Existing connector-worker and connector-cli suites still pass 25 tests.
8. **Smallest plausible correction and regression.** Reconcile authoritative minimal terminal state before resending a retained rejected result, including 400 failures, while retaining exact attempt identity and current access checks. Provide a durable validation-failure outcome without erasing the original output or dispatching again. Validation before first delivery also helps but must not strand journals created by older versions. Test invalid completed output, cancel, restart and a later queued request across the real connector/route pair. Assert that no replacement provider call occurs.
9. **Released/prototype/backlog.** Released native project connector behavior introduced before v0.66. It is not a context-history prototype gap. The README promises restart recovery, retained exact delivery and cancellation handling, but does not describe this permanent rejection loop.
10. **Challenge and limits.** The test preserves a successful valid-answer control. A private copy mutation removing answer trimming makes the rejected-answer observation fail with `unexpected success`; this proves the test reached the real output validator. The coordinating reviewer received the finding for independent source review. It does not prove database scheduler behavior, provider quality or the frequency of whitespace-only answers.

## FIN-01. Recipient rounding can make a valid allocation impossible to save

1. **Severity.** Medium. The defect blocks allocation for particular amounts and recipient weights. It does not persist a negative balance or destroy the previous allocation.
2. **Confidence and affected code.** High. Real computation and native rejection reproduced. `openplan/src/lib/measures/allocation.ts:1396-1399`; route `openplan/src/app/api/measures/[measureId]/periods/[periodId]/allocate/route.ts`, recipient-row construction and `replace_measure_period_allocation` call. Baseline and release commits above.
3. **Trigger and preconditions.** A return-to-source category has no minimum-per-recipient floor and its rounded shares exceed the available cents. The lexically last recipient has insufficient share to absorb the whole negative residual. Four equal recipients splitting $0.02 suffice. A larger case splits $1,000,000.01 across weights 1, 1, 1 and 0.
4. **Expected versus observed.** Return nonnegative shares that conserve cents under a stated residual rule, or explicitly refuse an unsupported rule. The real allocator returns `ok: true` with `[0.01,0.01,0.01,-0.01]`. The larger case returns three shares of $333,333.34 and one of -$0.01. Its sum invariant passes.
5. **Consequence.** The route sends these amounts into a table with `CHECK(amount >= 0)`. The database returns `23514`; the allocation cannot be recorded. Native reproduction confirms the prior $100 allocation remains unchanged after a negative replacement. Do not report this as lost money or persisted negative allocation.
6. **Evidence.** `evidence/financial-repro.cjs` imports the actual allocation source through TypeScript transpilation and runs both counterexamples. `financial-repro.json` records exact results. `evidence/finance-native.cjs/json` exercises the actual latest RPC and constraint on the owned stack. Legitimate $4 allocation and harmless source-comment controls survive. A private in-memory fault that zeroes returned shares fails the named amount assertion. No application file changed.
7. **Why checks miss it.** `measure-allocation-arithmetic.test.ts:445-488` protects the category residual floor, but the recipient residual path has no equivalent exhausted-recipient case. Conserving the sum does not imply each term is nonnegative. The existing allocation, reporting-pagination and native fund suites report 46 tests passed while these observations reproduce.
8. **Smallest plausible correction.** Apply a bounded residual distribution across recipients, preserving the declared deterministic ordering and disclosing changed rounding treatment. Reuse the category correction's principle without importing an unsupported ordinance choice. If the intended policy is unresolved, return a visible allocation refusal rather than a successful negative result.
9. **Regression boundary.** Verify equal tiny shares, a zero-weight last recipient at normal fund magnitudes, declared floors, weighted bases, nonnegative individual results and exact sums. Confirm native replacement succeeds for valid results and retains original rows on refusal. Decimal computation does not establish ordinance applicability.
10. **Disposition and independent challenge.** New released-code defect. Security and provider reviewers confirmed latest SQL preserves atomicity and enforces nonnegative amounts. The existing measure pagination limitation KL-036 is a different mechanism.

## FIN-02. Allocation RPC accepts a period belonging to another fund

1. **Severity.** Medium. This is a financial relationship-integrity defect within one authorized workspace, not cross-workspace privilege escalation.
2. **Confidence and affected code.** High, demonstrated on all 358 baseline migrations. `openplan/supabase/migrations/20260812000019_measure_period_reserve.sql:283-307,338-353`; `20260812000011_local_measure_fund.sql:464-473`. Baseline and release commits above.
3. **Trigger and preconditions.** An authenticated writer uses the directly callable `replace_measure_period_allocation` RPC, supplies fund B and a period actually owned by fund A, and writes a row naming the supplied fund and period. Both funds share the writer's workspace. The ordinary route's properly scoped period lookup does not produce this payload.
4. **Expected versus observed.** The database should require the period's real fund to equal the allocation fund. Instead, the RPC checks each JSON row against its arguments and the foreign keys separately enforce period/workspace and fund/workspace. The mismatched native call succeeds and retains a second allocation under the same period with the other fund ID. A foreign-workspace period is rejected with `23503`, establishing the separate tenant boundary.
5. **Consequence.** A stored allocation has contradictory fund ownership. Annual statements filter both fund and that fund's period IDs, so the malformed row can be omitted from both corresponding statements. It is not automatically double-counted. The claim category fallback queries by fund alone and can carry its category into the wrong fund. Period/category uniqueness can also block rightful entries.
6. **Evidence.** `evidence/finance-native.cjs/json` uses a synthetic authenticated owner and synthetic funds on API 29971 only. Matched fund/period and harmless rationale-change controls succeed; negative amount and foreign-workspace controls fail with the expected native constraint codes; same-workspace wrong-fund succeeds. Fixtures remain in the owned disposable stack. No production database or real financial data was used.
7. **Why checks miss it.** `openplan/src/test/measure-fund-rls.test.ts` checks cross-workspace parenting and submitted-claim deletion. Its composite-key assertion proves workspace consistency but cannot prove fund/period consistency. The existing suite passes. Native RLS and a schema inventory are insufficient when both contradictory parents are permitted to the same user.
8. **Smallest plausible correction.** Add data-safe composite period/fund/workspace constraints and equivalent relationship protection for off-the-top/reserve rows. Validate the parent pair before replacement. Inspect and explicitly reconcile existing mismatches before validating a new constraint. Do not discard records during migration.
9. **Regression boundary.** Direct authenticated RPC and direct table writes must reject same-workspace wrong-fund pairs, preserve existing rows on refusal and accept matched pairs. Include recipient/rule relationship checks where they affect source identity. Add a harmless valid-parent control and a targeted missing-parent-check mutation in an isolated schema.
10. **Disposition and independent challenge.** New released-code defect. Provider and science reviewers independently checked the latest migration chain and consequences. This is separate from unfinished recipient-organization access under M13 and from known unpaged measure reads.

## FIN-03. OWP reads silently stop at a server cap below 200

1. **Severity.** Medium, conditional on a supported self-host configuration. The repository's default `max_rows = 1000` does not trigger this specific defect.
2. **Confidence and affected code.** High in the executed algorithm; no native cap reconfiguration performed. `openplan/src/lib/programs/work-program/reporting-server.ts:11-20`; callers in `openplan/src/app/api/programs/[programId]/work-program/reporting/route.ts:21-42`, reimbursement and closeout readers. Baseline and release commits above.
3. **Trigger and preconditions.** Configure PostgREST to return fewer than 200 rows per request, with more source records than the cap. The synthetic transport supplies 250 records and caps each response at 50.
4. **Expected versus observed.** Read all rows or report incomplete data. The actual function returns 50 records after requesting range 0–199 once. It treats a short page as exhaustion. The same 250 records under the normal cap are all returned.
5. **Consequence.** OWP actuals, source lists, revisions, reimbursements and closure histories can appear incomplete without a failed-read state. This can affect management review and selection. This review does not claim an issued snapshot is corrupted, because the issue/valuation SQL paths are separate and were not reproduced under a reduced cap.
6. **Evidence.** `evidence/financial-repro.cjs/json` executes the actual named function extracted with the TypeScript parser. It records 250 versus 50 returned records. Harmless comment control survives; a fault that drops the append fails the named count assertion. The transport simulates the documented PostgREST cap. No current default deployment is claimed affected by the reproduction.
7. **Why checks miss it.** `work-program-reporting-pagination.test.ts:7-22` returns the entire requested slice, so its 1,201-record example never returns a short nonterminal page. Its projection assertions are useful and do not cover transport caps. The shared `readEveryPage` explicitly handles this case, but this reader does not use it.
8. **Smallest plausible correction.** Use the existing complete-read helper or advance by the number actually received and continue until an empty page. Keep deterministic ordering, cutoff and explicit error behavior. Apply the same review to the adjacent 100-row OWP preparation/history loops.
9. **Regression boundary.** Test 0, 1, 50, 200 and more than 200 records with smaller server caps, a later error, a stable immutable cutoff and no duplicate/lost rows. Do not simply increase the requested page size.
10. **Disposition and independent challenge.** New conditional released-code defect. Science review agrees with the algorithm finding and specifically rejects generalizing it to default `max_rows = 1000`. Existing KL-023/036 describe different older unpaged financial readers and do not close this OWP reader.

## UI-01. Dashboard submittal summary always queries a nonexistent column

1. **Severity.** Medium. The app visibly reports an unreadable source, but cannot summarize submittal-related work through this loader.
2. **Confidence and affected code.** High. Real browser and native database evidence agree. `openplan/src/lib/operations/workspace-summary.ts:1040-1044,1167-1171`; table definition `openplan/supabase/migrations/20260321000033_lane_c_lapm_pm_invoicing.sql:47` and later assignee migration.
