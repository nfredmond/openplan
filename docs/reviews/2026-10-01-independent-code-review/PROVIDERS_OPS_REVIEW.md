## Findings

### PROV-01. Financial routes accept writes outside the approved action payload

1. **Severity and confidence.** High severity. High confidence in the demonstrated route defect. The reproduction runs the real handler and approval verifier with mocked access and database operations. Native row-level security was not part of this reproduction.
2. **Affected commit and locations.** Baseline `891a0d89a848133d44b9e4f314a76a922cd71ace`. `openplan/src/app/api/projects/[projectId]/funding-profile/route.ts:76-97,120-125`; `openplan/src/lib/runtime/action-registry.ts:100-119`; `openplan/src/lib/assistant/action-approval-server.ts:280-409`. The registered action omits amount authority, while the route accepts amounts in its broader manual PATCH schema.
3. **Trigger and preconditions.** An authenticated workspace writer has an unconsumed, unexpired `create_project_funding_profile` approval for the correct project and notes. Submit the same source/hash/approval headers and approved notes, adding `fundingNeedAmount: 9999999` and `localMatchNeedAmount: 7777777`. This requires the already-authorized writer's session. It does not establish cross-tenant access or an unauthenticated privilege escalation.
4. **Expected and observed.** The route should reject financial fields outside the approved action, or bind them to explicit consent if the action is deliberately broadened. Instead, the route hashes only kind, project ID and notes, consumes the matching approval, submits both changed amounts to its upsert and returns HTTP 200. Changing the signed note returns 403 before consumption or upsert, proving the real hash protection was reached.
5. **Consequence.** A stored execution can claim exact Planner Agent approval while changing financial fields the approval never represented. The normal registry sends null amounts, so this finding is about route enforcement under altered requests, not a claim that the normal UI automatically chooses those injected values.
6. **Reproduction and evidence.** Run from the review root:

   ```sh
   openplan/node_modules/.bin/vitest run --config docs/reviews/2026-10-01-independent-code-review/evidence/providers-approval.vitest.config.ts
   ```

   `evidence/providers-approval.test.ts` supplies four observations: unchanged approved payload accepted, harmless JSON key ordering accepted, changed signed note rejected, unsigned amount changes accepted. `evidence/providers-approval-output.txt` records the combined six-test run with the native recovery reproduction. It does not claim a live financial write.
7. **Why checks miss it.** `openplan/src/test/project-funding-profile-route.test.ts:90-116` tests a manual PATCH without approval headers. `action-approval-server.test.ts` exercises hashes presented to the verifier, not whether every persisted route field reached that hash. A correct verifier cannot identify an omitted field it never receives. Four existing relevant suites still passed 126 tests alongside this defect. The current browser registry also cannot demonstrate a hostile addition because it emits fixed null amounts.
8. **Smallest plausible correction and regression.** For Planner Agent requests, reject every mutable field outside the narrow approved action or reconstruct the write entirely from that action. Keep manual financial editing explicit. Add actual-handler tests that append each manual-only field to a valid approved request and assert refusal before consumption/write. Preserve unchanged payload and manual-edit controls. Do not merely broaden the hash schema without deciding whether the agent should have financial authority.
9. **Released/prototype/backlog.** Released route behavior, independent of unfinished context-history work. This differs from known KL-2026-09-04-046, which records non-atomic approval/effect/audit and delegated-authorship gaps. Exact approved-field binding is separately defective here.
10. **Cross-review and related locations.** The coordinating reviewer independently confirmed the omitted fields. Source inspection finds the same class in `funding-opportunities/route.ts:368-382,411-437`, which hashes title/project/program but persists additional financial and decision fields; `funding-opportunities/[opportunityId]/route.ts:130-169,179-182`, which hashes only the decision while updating other supplied fields; and `invoicing/invoices/[invoiceId]/route.ts:161-172,192-208`, which hashes the award link but can update invoice status in the same request. These related routes are source-established and were not all reproduced with the real verifier. Consolidate them as one audit of action-to-write binding rather than separate counts.

The profile route also uses upsert on project ID. An old create proposal can overwrite a profile created after proposal preparation, including nulling its amounts through the normal registry. The route has no create-only or expected-version predicate. This source-established stale-proposal consequence needs a separate concurrent database reproduction before grading actual lost financial history.

### PROV-02. A rejected native answer blocks later connector jobs, including after cancellation

1. **Severity and confidence.** Medium severity. High confidence in the demonstrated recovery behavior. Production connector and native route are composed together; database and native provider generation are synthetic.
2. **Affected commit and locations.** Baseline `891a0d89a848133d44b9e4f314a76a922cd71ace`. `workers/planner_agent_connector/connector-worker.mjs:64-74,113-136`; `openplan/src/app/api/assistant/providers/native/route.ts:42-63`; `workers/planner_agent_connector/connector.mjs:77-87`; `openplan/src/lib/assistant/provider-project-task.ts:43-58`.
3. **Trigger and preconditions.** A native provider returns a completed answer that passes the connector's identity/string/byte checks but fails the application's output parser. The synthetic answer is valid JSON with the correct citation, `submittal: null`, and whitespace-only `answer`. This needs no oversized or malformed transport. The app rejects the trimmed empty answer. Actual provider frequency was not measured.
4. **Expected and observed.** Preserve the exact observed output and allow the attempt to reach a terminal rejection or cancellation, without generating again. The route instead returns 400 before the finish RPC. The connector has already synced a `completed` journal and reconciles terminal status only after HTTP 409. Recovery repeatedly resends the same invalid answer. Even after the database state becomes `cancelled`, the route parses the answer before reaching its finish RPC and again returns 400. Continuous mode labels this `connection_unavailable` and loops.
5. **Consequence.** One rejected result prevents all subsequent claims on that personal connection. Restart and ordinary cancellation do not clear the journal. The model is not called again, so this finding is blocked progress and misleading recovery guidance, not duplicate provider spending. Creating a new connection/directory is a workaround, with original evidence retained separately.
6. **Reproduction and evidence.** `evidence/providers-native-recovery.test.ts` runs actual `connectorCycle` and actual native `POST`. Its valid control records one claim, one generation and one successful finish. The rejected-answer case records statuses `[400,400,400]`, one claim, one generation, zero finish RPCs and journal phase `completed`. The last two cycles occur after the synthetic database returns cancelled state. Run with the same command as PROV-01.
7. **Why checks miss it.** `workers/planner_agent_connector/test/connector-worker.test.mjs:24-34` stubs every finish as success/failure without running the application's output parser. Its fixture answer lacks fields the real parser requires. Native route/parser tests and connector tests exercise their own boundaries separately. The connector's existing cancellation recovery probes return 409, which is the one code its recovery branch handles. Existing connector-worker and connector-cli suites still pass 25 tests.
8. **Smallest plausible correction and regression.** Reconcile authoritative minimal terminal state before resending a retained rejected result, including 400 failures, while retaining exact attempt identity and current access checks. Provide a durable validation-failure outcome without erasing the original output or dispatching again. Validation before first delivery also helps but must not strand journals created by older versions. Test invalid completed output, cancel, restart and a later queued request across the real connector/route pair. Assert that no replacement provider call occurs.
9. **Released/prototype/backlog.** Released native project connector behavior introduced before v0.66. It is not a context-history prototype gap. The README promises restart recovery, retained exact delivery and cancellation handling, but does not describe this permanent rejection loop.
10. **Challenge and limits.** The test preserves a successful valid-answer control. A private copy mutation removing answer trimming makes the rejected-answer observation fail with `unexpected success`; this proves the test reached the real output validator. The coordinating reviewer received the finding for independent source review. It does not prove database scheduler behavior, provider quality or the frequency of whitespace-only answers.

## Independent challenge of the ActivitySim HTTP finding

`workers/activitysim_worker/main.py:104-108` only checks the token when the configured value is nonempty. The Docker entrypoint runs gunicorn on all interfaces. `_parse_payload` accepts caller-selected output directory and force. `runtime.py:582-586` calls `prepare_runtime_directory` before stage validation; `runtime.py:536-545` resolves that directory and removes an existing tree when force is true. A reachable manual HTTP worker with token omitted and a writable target therefore has a direct destructive path. An existing resolvable bundle manifest is a precondition for the actual runtime path. Network reachability and available filesystem permissions bound impact. DEPLOY's token example is configuration advice, not a fail-closed implementation. This is separate from the known long-stage reaper and late-worker concerns.

The scientific reviewer owns demonstration and severity of that finding. This report adds independent source confirmation and does not double-count it. The documented `python main.py --serve` command also lacks the argparse-required source argument. That setup defect is secondary to the authorization finding and has not been promoted as another security finding.

## Recommended implementation order

First close the manually exposed ActivitySim HTTP authorization/destructive-path finding described in the scientific report, if that server is deployed. Then audit every action route for mutable fields outside its approved payload, starting with finance and invoice status. Fix PROV-01 as a route boundary, retaining narrow agent authority. Next fix PROV-02 with terminal-state reconciliation and durable invalid-output handling. Keep the known effect/receipt transaction and broader operations work in their roadmap lanes.

No finding in this subreview is marked resolved by a development change. This report does not establish whole-repository security, production recovery, practitioner usefulness or v1 readiness.

## Independent challenge of the measure-allocation finding

Source review agrees with the coordinating reviewer's native reproduction in `evidence/finance-native.json`. The latest five-argument `replace_measure_period_allocation` definition checks each row against the supplied fund and period IDs, but never verifies that the selected period belongs to that fund. Separate workspace composite foreign keys do not enforce that relationship. No subsequent function replacement or table trigger repairing it was found in the migration search.

Medium severity is proportionate for a direct authenticated writer/API integrity defect. Annual statement reads filter both the fund and that fund's period IDs at `openplan/src/app/api/measures/[measureId]/statement/route.ts:195-199`, so the malformed cross-fund row disappears from both funds' corresponding statements. This is not evidence of automatic double counting. The claims narrative fallback reads category IDs by fund alone at `claims/route.ts:166-168`, which can propagate a category from the wrong fund's period. Period/category unique indexes can also collide with a rightful allocation. The root report owns the finding and native evidence; this note records an independent consequence check.
