## FIN-01. Recipient rounding can make a valid allocation impossible to save

1. **Severity.** Medium. The defect blocks allocation for particular amounts and recipient weights. It does not persist a negative balance or destroy the previous allocation.
2. **Confidence and affected code.** High. Real computation and native rejection reproduced. `openplan/src/lib/measures/allocation.ts:1396-1399`; route `openplan/src/app/api/measures/[measureId]/periods/[periodId]/allocate/route.ts`, recipient-row construction and `replace_measure_period_allocation` call. Baseline and release commits above.
3. **Trigger and preconditions.** A return-to-source category has no minimum-per-recipient floor and its rounded shares exceed the available cents. The lexically last recipient has insufficient share to absorb the whole negative residual. Four equal recipients splitting $0.02 suffice. A larger case splits $1,000,000.01 across weights 1, 1, 1 and 0.
4. **Expected versus observed.** Return nonnegative shares that conserve cents under a stated residual rule, or explicitly refuse an unsupported rule. The real allocator returns `ok: true` with `[0.01,0.01,0.01,-0.01]`. The larger case returns three shares of $333,333.34 and one of -$0.01. Its sum invariant passes.
5. **Consequence.** The route sends these amounts into a table with `CHECK(amount >= 0)`. The database returns `23514`; the allocation cannot be recorded. Native reproduction confirms the prior $100 allocation remains unchanged after a negative replacement. Do not report this as lost money or persisted negative allocation.
6. **Evidence.** `evidence/financial-repro.cjs` imports the actual allocation source through TypeScript transpilation and runs both counterexamples. `financial-repro.json` records exact results. `evidence/finance-native.cjs/json` exercises the actual latest RPC and constraint on the owned stack. Legitimate $4 allocation and harmless source-comment controls survive. A private in-memory fault that zeroes returned shares fails the named amount assertion. No application file changed.
7. **Why checks miss it.** `measure-allocation-arithmetic.test.ts:445-488` protects the category residual floor, but the recipient residual path has no equivalent exhausted-recipient case. Conserving the sum does not imply each term is nonnegative. The existing allocation, reporting-pagination and native fund suites report 46 tests passed while these observations reproduce.
8. **Smallest plausible correction.** Apply a bounded residual distribution across recipients, preserving the declared deterministic ordering and disclosing changed rounding treatment. Reuse the category correction's principle without importing an unsupported ordinance choice. If the intended policy is unresolved, return a visible allocation refusal rather than a successful negative result.
9. **Regression boundary.** Verify equal tiny shares, a zero-weight last recipient at normal fund magnitudes, declared floors, weighted bases, nonnegative individual results and exact sums. Confirm native replacement succeeds for valid results and retains original rows on refusal. Decimal computation does not establish ordinance applicability.
10. **Disposition and independent challenge.** New released-code defect. Security and provider reviewers confirmed latest SQL preserves atomicity and enforces nonnegative amounts. The existing measure pagination limitation KL-036 is a different mechanism.

## FIN-02. Allocation RPC accepts a period belonging to another fund

1. **Severity.** Medium. This is a financial relationship-integrity defect within one authorized workspace, not cross-workspace privilege escalation.
2. **Confidence and affected code.** High, demonstrated on all 358 baseline migrations. `openplan/supabase/migrations/20260812000019_measure_period_reserve.sql:283-307,338-353`; `20260812000011_local_measure_fund.sql:464-473`. Baseline and release commits above.
3. **Trigger and preconditions.** An authenticated writer uses the directly callable `replace_measure_period_allocation` RPC, supplies fund B and a period actually owned by fund A, and writes a row naming the supplied fund and period. Both funds share the writer's workspace. The ordinary route's properly scoped period lookup does not produce this payload.
4. **Expected versus observed.** The database should require the period's real fund to equal the allocation fund. Instead, the RPC checks each JSON row against its arguments and the foreign keys separately enforce period/workspace and fund/workspace. The mismatched native call succeeds and retains a second allocation under the same period with the other fund ID. A foreign-workspace period is rejected with `23503`, establishing the separate tenant boundary.
5. **Consequence.** A stored allocation has contradictory fund ownership. Annual statements filter both fund and that fund's period IDs, so the malformed row can be omitted from both corresponding statements. It is not automatically double-counted. The claim category fallback queries by fund alone and can carry its category into the wrong fund. Period/category uniqueness can also block rightful entries.
6. **Evidence.** `evidence/finance-native.cjs/json` uses a synthetic authenticated owner and synthetic funds on API 29971 only. Matched fund/period and harmless rationale-change controls succeed; negative amount and foreign-workspace controls fail with the expected native constraint codes; same-workspace wrong-fund succeeds. Fixtures remain in the owned disposable stack. No production database or real financial data was used.
7. **Why checks miss it.** `openplan/src/test/measure-fund-rls.test.ts` checks cross-workspace parenting and submitted-claim deletion. Its composite-key assertion proves workspace consistency but cannot prove fund/period consistency. The existing suite passes. Native RLS and a schema inventory are insufficient when both contradictory parents are permitted to the same user.
8. **Smallest plausible correction.** Add data-safe composite period/fund/workspace constraints and equivalent relationship protection for off-the-top/reserve rows. Validate the parent pair before replacement. Inspect and explicitly reconcile existing mismatches before validating a new constraint. Do not discard records during migration.
9. **Regression boundary.** Direct authenticated RPC and direct table writes must reject same-workspace wrong-fund pairs, preserve existing rows on refusal and accept matched pairs. Include recipient/rule relationship checks where they affect source identity. Add a harmless valid-parent control and a targeted missing-parent-check mutation in an isolated schema.
10. **Disposition and independent challenge.** New released-code defect. Provider and science reviewers independently checked the latest migration chain and consequences. This is separate from unfinished recipient-organization access under M13 and from known unpaged measure reads.

## FIN-03. OWP reads silently stop at a server cap below 200

1. **Severity.** Medium, conditional on a supported self-host configuration. The repository's default `max_rows = 1000` does not trigger this specific defect.
2. **Confidence and affected code.** High in the executed algorithm; no native cap reconfiguration performed. `openplan/src/lib/programs/work-program/reporting-server.ts:11-20`; callers in `openplan/src/app/api/programs/[programId]/work-program/reporting/route.ts:21-42`, reimbursement and closeout readers. Baseline and release commits above.
3. **Trigger and preconditions.** Configure PostgREST to return fewer than 200 rows per request, with more source records than the cap. The synthetic transport supplies 250 records and caps each response at 50.
4. **Expected versus observed.** Read all rows or report incomplete data. The actual function returns 50 records after requesting range 0–199 once. It treats a short page as exhaustion. The same 250 records under the normal cap are all returned.
5. **Consequence.** OWP actuals, source lists, revisions, reimbursements and closure histories can appear incomplete without a failed-read state. This can affect management review and selection. This review does not claim an issued snapshot is corrupted, because the issue/valuation SQL paths are separate and were not reproduced under a reduced cap.
6. **Evidence.** `evidence/financial-repro.cjs/json` executes the actual named function extracted with the TypeScript parser. It records 250 versus 50 returned records. Harmless comment control survives; a fault that drops the append fails the named count assertion. The transport simulates the documented PostgREST cap. No current default deployment is claimed affected by the reproduction.
7. **Why checks miss it.** `work-program-reporting-pagination.test.ts:7-22` returns the entire requested slice, so its 1,201-record example never returns a short nonterminal page. Its projection assertions are useful and do not cover transport caps. The shared `readEveryPage` explicitly handles this case, but this reader does not use it.
8. **Smallest plausible correction.** Use the existing complete-read helper or advance by the number actually received and continue until an empty page. Keep deterministic ordering, cutoff and explicit error behavior. Apply the same review to the adjacent 100-row OWP preparation/history loops.
9. **Regression boundary.** Test 0, 1, 50, 200 and more than 200 records with smaller server caps, a later error, a stable immutable cutoff and no duplicate/lost rows. Do not simply increase the requested page size.
10. **Disposition and independent challenge.** New conditional released-code defect. Science review agrees with the algorithm finding and specifically rejects generalizing it to default `max_rows = 1000`. Existing KL-023/036 describe different older unpaged financial readers and do not close this OWP reader.

## UI-01. Dashboard submittal summary always queries a nonexistent column

1. **Severity.** Medium. The app visibly reports an unreadable source, but cannot summarize submittal-related work through this loader.
2. **Confidence and affected code.** High. Real browser and native database evidence agree. `openplan/src/lib/operations/workspace-summary.ts:1040-1044,1167-1171`; table definition `openplan/supabase/migrations/20260321000033_lane_c_lapm_pm_invoicing.sql:47` and later assignee migration. Baseline and release commits above.
3. **Trigger and preconditions.** Open the dashboard against the baseline schema, including a fresh installation. No submittal records are required. The summary filters `project_submittals.workspace_id`; this table belongs to a workspace through `projects` and has no direct workspace column.
4. **Expected versus observed.** The workspace summary should read authorized project submittals through their parent project. Native PostgREST returns `42703`, `column project_submittals.workspace_id does not exist`. The dashboard says project submittals could not be read. Repeating the read cannot repair a schema mismatch.
5. **Consequence.** Project submittals do not contribute to this dashboard's operational summary or reimbursement-submittal context. The honest unreadable warning prevents treating it as a fully successful empty read, but does not restore the missing workflow information. Other direct project submittal pages were not found broken by this reproduction.
6. **Evidence.** `evidence/dashboard-native.cjs/json` extracts and executes the exact source query against the review-owned database. The same error occurs with a harmless comment. A query using the real project relationship column succeeds. Browser navigation proceeds from home through real registration, sign-in and dashboard, at desktop and 390 CSS pixels. `evidence/browser-identity.txt` confirms the dev launch belongs to this checkout. Screenshots and browser observations are retained separately.
7. **Why checks miss it.** `openplan/src/test/workspace-summary.test.ts:43` implements `.eq` as an unconditional chain operation. The mocks return rows by table without validating the schema/filter relationship. The generic source-read warning test checks the fallback, not whether production can issue a valid query.
8. **Smallest plausible correction.** Scope the read through the actual projects relationship, using the existing portfolio-query pattern. Preserve tenant authorization and the unreadable state for real failures. Do not remove the warning to make the dashboard appear healthy.
9. **Regression boundary.** Run the actual joined query on a fresh native schema with two workspaces, plus authorized empty/nonempty controls and an unavailable-source case. Assert its projection and relationship filter in focused tests. Browser checks should confirm the warning clears only when the query succeeds.
10. **Disposition and independent challenge.** New released-code integration defect. The provider/operations reviewer independently confirmed the absent column and mock blind spot. It is not a known missing v1 module or a defect in the context-history prototype.
