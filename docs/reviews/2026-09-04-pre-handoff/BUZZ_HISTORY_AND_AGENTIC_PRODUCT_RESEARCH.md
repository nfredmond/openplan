# Buzz history and agentic planning product research

Dated 2026-09-04. Research and product recommendations only. No implementation, service, browser, account, database or model work was performed. The sole file written is this report.

## Finding

The durable goal is that a planner can assign substantial work across OpenPlan, inspect the evidence and proposed changes, and retain responsibility for consequential decisions. Buzz was a concrete proposed workspace for that goal. The accepted MCP decision preserves an optional external route into the same OpenPlan capabilities and approvals.

**A provider picker, chat response or callable tool list does not complete that goal.** The product needs durable assigned work, visible progress and blockers, source-linked artifacts, reviewable changes and reliable handoff after interruption. Existing Planner Agent, My Work, Documents, case records and approval machinery are the starting point. OpenPlan must remain complete without Buzz or an agent.

## What current Buzz could contribute, and what it would impose

Buzz’s first-party README describes a self-hosted human/agent workspace with rooms, signed events, search and separate agent identities. It distinguishes the complete workspace from its constituent binaries. Its production deployment includes Postgres, Redis and object storage; adopting it adds operational and identity integration work. The README still lists workflow approval gates as being wired up. Its authors’ maturity table is documentation, not independent OpenPlan acceptance. [Pinned Buzz README](https://github.com/block/buzz/blob/f038cbbb0d4092a72ffd93f17916f84d2b39bb43/README.md), direct lines 29–40, 99–105, 178, 228–230.

The useful design reference is shared work with visible agent authorship and an inspectable record. The separate `buzz-agent` and `buzz-dev-mcp` components compose through ACP and MCP. The latter supplies a shell/file editor at the operator’s trust level, which is a coding capability rather than an agency case-permission system. [Pinned agent vision](https://github.com/block/buzz/blob/f038cbbb0d4092a72ffd93f17916f84d2b39bb43/VISION_AGENT.md), direct lines 9–22, 53–64. OpenPlan should expose typed planning reads/proposals rather than give that shell authority over its database or private files.

The pinned `buzz-agent` README documents important limits: MCP transport is stdio-only; sessions are in memory and cannot be loaded after restart; the launching operator and configured tools are trusted. Oversized tool schemas are replaced with an empty schema, and its reply guard recognizes an attempted message command rather than successful delivery. These are documented boundaries, not tested defects here. [Pinned runtime README](https://github.com/block/buzz/blob/f038cbbb0d4092a72ffd93f17916f84d2b39bb43/crates/buzz-agent/README.md), direct lines 211–219, 293–303, 325, 337–345.

Consequently, ADR-004’s “Phase 4 is configuration” is not established for this runtime against the proposed remote HTTP MCP endpoint. A compatible client or tested adapter, secure identity mapping, exact approval continuation and persistent OpenPlan job records are still necessary. A configured tool or attempted reply cannot certify completion. This conclusion is an interoperability inference, not a claim that every Buzz client has the same transport limit.

The repository’s [Apache 2.0 license](https://github.com/block/buzz/blob/f038cbbb0d4092a72ffd93f17916f84d2b39bb43/LICENSE) supports evaluating reuse with its redistribution/notice conditions. It does not establish compatibility, professional fitness or an obligation to run a second platform. Root’s framework survey should decide whether particular components earn their integration cost. No new provider subscriptions, shared personal entitlement or hosted infrastructure is assumed.

ADR-004’s protocol revision, MRTR, SDK versions, self-hosted OAuth availability and library examples require fresh official implementation research. This report preserves the approved product/control rationale without certifying those old wire details. The prior `PLANNER_AGENT_PROVIDER_RESEARCH.md:40–59` already separates person/device connection, actual entitlement, local pairing, bounded context, durable execution and human acceptance. An arbitrary browser cannot launch an installed CLI on the visitor’s computer without an explicitly installed and paired mechanism.

## Product positioning and experience

Position the Planner Agent around completing assigned planning work with an accountable reviewer. A useful promise is: “Give OpenPlan a planning task. Review the sources, proposed changes and finished record.” Until demonstrated, this is the proposed destination, not marketing copy claiming present capability.

The source already contains module context targets, typed proposals and execution states (`openplan/src/lib/assistant/catalog.ts:26–56`; `openplan/src/components/assistant/app-copilot.tsx:52–83,531–675`). It also contains operation filters, pins and snoozes. Do not claim the current product is merely a blank chat box or replace working controls before evaluating them.

Extend that foundation with a persistent case assignment accessible from the actual plan/project and My Work. The planner should see the selected authority and source set, intended deliverable, execution device/provider, steps, blockers and stop/resume state. Working drafts, maps, tables and proposed field changes should be inspectable next to their sources. Review should show exact before/after content and dependent consequences, with a readable human summary above the full details. After approval, the receipt should name what actually changed, what failed and what remains unresolved.

Conversation remains useful for direction and clarification. Durable facts belong to case records and evidence, not hidden reasoning or a chat summary. A new staff member must understand and continue the task without replaying the entire conversation. A planner can change a draft manually, and the agent must then work from the real revised version. An optional Buzz room can discuss the work, but OpenPlan remains authoritative for approvals and planning records.

## Autonomy boundaries that keep the work useful

Allow authorized reading, source retrieval, deterministic calculation, working-draft preparation, gap explanation and proposal assembly within the assigned case. A planner need not approve every sentence before seeing a draft. But persistence, tools and transitions must follow the actual registered capability and current permission policy; a chat instruction is not a general administrative credential.

Consequential publication, responses to the public, proposal submission, award, adoption, certification, money and new factual claims remain human-controlled. Show and bind the exact consequence being approved. For a reviewed group of related changes, retain inspectable individual effects and dependency order; any future batch approval requires a separately proven design. This research does not authorize bypassing the present proposal rules for supposedly harmless actions.

Separate the delegating person, executing agent/provider/device and legal approver. Revocation or staff departure stops new access. Provider change must disclose context transfer and spending implications. Scheduled internal summaries require an explicit authorized scope and operating connection; they cannot borrow the last user’s personal subscription. Restrict untrusted document instructions and external-tool content to evidence, never policy or permission changes.

Long model/processing jobs remain durable workers. Stopping an agent turn must not silently destroy another owner’s work, reopen holdouts or relabel an incomplete run successful. Keep AequilibraE and ActivitySim separate and preserve inconclusive/unknown states. Agent summaries cannot substitute for deterministic numbers, independent scientific validation or accountable agency decisions.

## Sequencing and proof

1. Keep expanding registered reads/proposals or explicit refusals when underlying features ship. Establish a job-to-required-context/action matrix so complete RTP, capital and funding work cannot disappear behind a large tool count.
2. Complete early A0 provider choice on one already-supported planning task, with real installation/authentication and the same approval path. This proves connection and a bounded outcome, not whole-product control.
3. Deliver persistent assignment/review/recovery for one substantial proven workflow. Select it against current task readiness and the user’s priorities. Measure agency usefulness before proliferating autonomous roles.
4. Expose equivalent scoped reads and proposals through a currently verified MCP protocol and actual compatible external client. Prove permission, source and approval parity with the in-app route. Evaluate optional Buzz connection against the pinned runtime and its added operations burden.
5. Extend the required cases above and the full practice/organization matrix. Keep unsupported jobs explicit until each underlying workflow and agent route pass.

Before observing outcomes, define task inputs, required outputs, unacceptable mistakes and how completion will be judged. Compare the same work through the ordinary UI and agent-assisted route with practicing planners and actual recipients. Measure final artifact correctness, source coverage, time including review/correction, interventions, recovery success and whether users understand what changed. Set practical success criteria before the evaluation; this report invents no time-saving percentage or scientific threshold. Faster production of an unusable report fails.

At the technical gate, challenge wrong tenant/case, stale source, altered approved payload, repeated execution after reconnect, refused action, tool error reported as success, truncated result, source prompt injection, quota exhaustion and revoked device. Every changed guard needs a harmless surviving mutation and a targeted failure. Human observation must establish usefulness separately. A stopped loop, attempted tool call, green suite or confident final message cannot substitute for persisted outcomes and an independent recipient’s usable artifact.
