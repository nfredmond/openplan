Nathaniel's requirement is binding: complete the existing drone operations module with the substantial capabilities of current OpenDroneMap and WebODM, then establish better planning usefulness through comparative evidence. ## Decision

Extend the existing Aerial mission, photo, processing and evidence records. Keep the present NodeODM integration while repairing correctness and recovery. Introduce a versioned processing-engine adapter and run a bounded compatibility/quality trial of NodeODX before selecting any replacement. Reuse upstream photogrammetry; do not build another structure-from-motion engine or adopt a second full agency workspace merely to obtain a viewer.

Current WebODM became independent from OpenDroneMap in April 2026 and publishes ODX/NodeODX forks. This means the two named benchmarks must be assessed separately. An old description of WebODM as only an ODM interface is no longer sufficient. Pin exact versions, options, engine identity and outputs in every processing run. Never relabel an old ODM result as ODX, silently change a historical run or compare only product names. [Official separation announcement](https://webodm.org/blog/announcement/), [OpenDroneMap project](https://opendronemap.org/), [current WebODM](https://webodm.org/).

Use [the feature benchmark](ODM_WEBODM_FEATURE_BENCHMARK.md), [current code review](AERIAL_CURRENT_CAPABILITY_REVIEW.md) and [DJI research](DJI_MISSION_EXPORT_USB_RESEARCH.md) as detailed evidence. The user-supplied SkyeBrowse comparison is a commercial perspective; the 2019 Reddit discussion is historical context. Neither establishes present output accuracy or controller compatibility.

The existing Aerial Intel decoder receives the whole input and allocates it in WASM, then caps rendered points by striding (default 1.5 million). That is not out-of-core access for a huge cloud. Its volume estimator uses gridded maximum heights over a fitted base plane and records sampled/filled-cell counts. Its viewer formats measurements as metres. Reuse must establish actual horizontal/vertical CRS, unit conversion, decimation error and missing-cell coverage. Display subsampling must not silently become engineering quantity evidence. Build an independent analytical path when full-resolution measurement is needed.

## What needs correction first

1. **Mission intent and file content can diverge.** The save route accepts an arbitrary generated-plan object and fingerprints the separately supplied parameters. The export parser then uses snapshot altitude and speed. Root independently traced the route and exporter. A fingerprint that catches stale edits does not validate the submitted geometry. Validate or regenerate the canonical snapshot on the server, preserve its reviewed version, and reject disagreement. The stored return-home altitude also never reaches the current export builder.
2. **DJI compatibility is an assumption in source.** The exporter omits aircraft/payload identification on the claim Pilot 2 will bind it automatically; the reviewed primary documentation does not establish that guarantee. It also omits template Folder content. Resolve exact profile/schema requirements, parse independently, then test the actual controller. No controller rejection was reproduced here.
3. **Worker restart does not restore a job.** Job/queue/artifact registries are in memory. The callback receipt is inserted before business application; after a downstream database failure the same callback ID receives a successful deduplication response without replaying unfinished application. Root independently traced that ordering. Persist engine-task identity and receipt/application states, reconcile unfinished work and prove duplicate/out-of-order behavior.
4. **Completeness and large jobs are unproven.** The worker does not deliver meshes. The UI accepts DNG but worker intake selects other extensions, so mixed input can lose photos. Output custody has HTTP/memory limits and no established resumable multi-gigabyte path. Persist exact input and required-output manifests; a completed orthomosaic is not completion of every requested product.

These are source findings, not runtime reproductions. Existing frozen evidence is preserved. Technical custody, successful processing, positional accuracy and fitness for a particular planning or engineering use remain different states.

## Full capability and comparative acceptance

M5b.1–6 owns the detailed work. Its completion evidence must cover collection planning and operations, reliable photo/control intake, orthomosaics, classified clouds, DSM/DTM, textured meshes and 3D tiles, calibration and checkpoints, multispectral/thermal uses supported by appropriate sensor inputs, 2D/3D inspection, measurements and surfaces, contours, time comparison, interoperable exports, permissions/sharing/localization and installation/operations. Upstream availability is not OpenPlan reachability. Unsupported combinations can be honestly disclosed during intermediate releases; disclosure alone does not satisfy the full target.

Use the same permitted input datasets for version-pinned comparator trials. Cover small and large RGB collections, oblique/corridor geometry, challenging surfaces, relevant calibrated spectral data and changes over time; record excluded cases. Assess independent checkpoint residuals, completeness, known quantities, missing coverage, output interoperability and processing/resource costs. Freeze reference/checkpoint roles and criteria before evaluating results; do not tune on consumed accuracy checks. Preserve unknown control heights rather than filling them with zero.

“Better” must be earned through both retained baseline capabilities and observed outcomes: fewer errors and less work from flight planning through checked outputs to a plan, inspection record, grant exhibit or capital progress decision; understandable limitations; reliable interruption recovery; and independent recipient reuse. Record time, corrections, task completion, uncertainty and participant judgment against each comparator. Do not claim a better reconstruction engine from a better interface. Drone imagery alone does not certify construction quantities, payment entitlement, regulatory compliance or structural condition.

## DJI KML and USB: an actual end-to-end requirement

Provide distinct survey-boundary KML, review-route KML and supported complete mission packages. DJI Pilot 2 documents survey geometry import for KML and full route packages using WPML inside KMZ. Computer copying precedes an explicit import in the controller app. Other DJI apps differ; DJI Fly's official help rejects KML route import. [DJI enterprise import/export instructions](https://repair.dji.com/help/content?customId=01700043570&lang=zh-CN&paperDocType=ARTICLE&re=CN&spaceId=17), [DJI Fly waypoint help](https://repair.dji.com/help/content?customId=01700007343&documentType=&lang=en&paperDocType=ARTICLE&re=US&spaceId=17).

The first supported combination should match Nathaniel's actual aircraft, payload, controller and app. Those details have been requested and are still unknown. This does not block specification and code repair, but hardware support cannot be established without them. Preserve separate states for generated, copied, imported, preview-reviewed and flight-validated. A USB cable and ordinary browser do not establish unrestricted controller-storage access. Start with verified download plus guided OS copy; add a narrowly paired local transfer helper if required to deliver the intended ease of use. Manual SD-card transfer is a useful fallback but does not close the direct-USB requirement.

Bench acceptance must verify exact file content, destination, app import/reopen, geometry, height reference, camera actions, return/loss settings and any defaults changed by the controller. Include disconnect, wrong profile, denied access, full storage and import rejection. Compare re-exported semantics where possible. Import acceptance must not initiate a flight. Later field validation requires the responsible qualified operator and an authorized operation.

## Sequence, operating cost and product decisions

First repair integrity/recovery and establish the user's controller profile; then complete output delivery and reusable viewer/measurement integration. Build control/accuracy and operational evidence alongside those workflows, followed by larger, spectral and repeat-survey cases. This sequence can proceed with ordinary planning, engagement and capital milestones; drone processing does not displace the rest of v1.

Measure source/output/backup expansion, peak RAM/GPU memory, temporary disk, queue delay, energy, import/export time and technician effort on local hardware before proposing hosted capacity. No installer, package, model weight, engine image or paid resource was downloaded or provisioned during this review. Maintain workload admission and recoverable queues so aerial work cannot exhaust the interactive planning application.

Nathaniel's product judgment is needed for the first actual equipment and permitted field case, which outputs support a planning judgment versus payment/survey/inspection, and public derivative/retention responsibilities. Engineering owns formats, architecture, reuse, failure handling, performance measurement and evidence quality. No new product implementation was launched by this research checkpoint.
