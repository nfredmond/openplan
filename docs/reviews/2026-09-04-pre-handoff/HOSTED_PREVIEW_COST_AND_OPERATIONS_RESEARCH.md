## Recommendation and scope

Prepare a reproducible, single-US-VM reference deployment with production Supabase Docker Compose, the production Next.js application, durable storage, and supervised workers. Start the sizing proposal at 16 GiB RAM, with resource limits separating routine workers from the database and web application. Run large demand-model, imagery, or other intensive jobs on a separate worker machine. Keep this deployment recipe usable on customer-owned computers and servers. Paid hosting, implementation, administration, customization, and support are optional services around the free software.

For a small invited trial, propose **$150–200/month for the base service and a bounded variable allowance**, before tax and operator labor. A 32–64 GiB model worker adds approximately **$25–50 for 100 allocated hours**, or **$168–336/month if kept allocated continuously**, under the specific bundled plans below. Those are equipment costs, not evidence that any particular county or model fits. An always-allocated large worker puts the proposed combined allowance around **$320–540/month**. None of these figures authorize expenditure or promise a user count.

The mid-term target remains a functioning browser-accessible OpenPlan trial: real persistence, separate user workspaces, uploads, planning workflows, exports, and actual queued execution for the capabilities advertised. It must remain independent of Nathaniel's computer being awake. A tunnel to a development stack, a static walkthrough, or a database that sleeps is not that target. Resource admission limits and queues are legitimate; hidden disabled core workflows or simulated success are not. Hosting alone cannot make currently incomplete product capabilities complete or demand-model outputs scientifically validated.

Use managed Supabase plus a managed Next.js host if the self-managed database/patching burden is untenable. It is a credible alternative, not a way to eliminate the workers, storage recovery, or application-security work. Avoid Kubernetes and a new orchestration platform for the initial reference installation unless a measured requirement establishes a need.

## Production Supabase is a separate deployment path

Supabase explicitly distinguishes its CLI local-development stack from self-hosting: the CLI stack is not hardened for production and must not face external traffic. Official self-hosting uses Docker Compose. The operator owns security updates, PostgreSQL maintenance, backups, availability and monitoring; managed platform capabilities such as managed backups/PITR and branching are not automatically supplied. [Supabase self-hosting](https://supabase.com/docs/guides/self-hosting)

For all Supabase components, the published minimum is **4 GB RAM, two CPU cores, 40 GB SSD**; recommendation **8 GB+, four cores+, 80 GB+ SSD**. This is Supabase's floor, not a capacity estimate for Supabase plus Next.js builds, geospatial processing, uploads and every OpenPlan worker. Supabase's Docker guide also requires production HTTPS, replacement of defaults, and explicit public/auth URLs. Its configuration and container versions must be pinned and rehearsed; do not silently transplant the CLI container names or mount paths. [Docker deployment requirements](https://supabase.com/docs/guides/self-hosting/docker)

The 16 GiB recommendation is engineering headroom, not a measured minimum. An 8 GiB machine is a cheaper candidate for a tightly bounded acceptance trial if tests show sufficient headroom. A 4 GiB full-stack host should not be advertised as the dependable reference merely because containers start. Build outside the serving host when practical, and measure peak RSS, disk amplification and latency under simultaneous uploads, exports and one admitted worker job.

## Storage, backups, email, maps and other variable costs

**Off-host storage:** Spaces Standard is $5/month for 250 GiB stored and 1,024 GiB outbound; excess storage $0.02/GiB-month and outbound $0.01/GiB. This can hold encrypted backup archives initially. Count all retained generations, uploaded files, worker outputs and temporary staging; 250 GiB is not 250 GiB of live project data plus unlimited history. Another bucket in the same provider/account is off-host, but not protection against loss of that entire account. [Spaces pricing, provider-verified July 13, 2026](https://docs.digitalocean.com/products/spaces/details/pricing/)

For a separate-provider copy, Backblaze B2 now costs $6.95/TB-month, with three times average stored data as included egress, then $0.01/GB. Its May 1, 2026 change supersedes $6/TB guidance. For illustration, 0.25 TB is roughly $1.74/month before allowances, rounding and other charges; budget $5–10 for an initial encrypted backup copy rather than presenting that arithmetic as an invoice guarantee. Standard API calls became free, with product-specific exceptions. Keep US region and retention/immutability configuration explicit. [Current B2 pricing](https://www.backblaze.com/cloud-storage/pricing), [March 17 announcement effective May 1](https://www.backblaze.com/blog/backblaze-pricing-and-product-updates/)

**Email:** current Resend pricing lists free 3,000 emails/month with 100/day; Pro $20/month for 50,000, overage $0.90/1,000. A low-volume invited trial might use free email, reducing the tables by $20, but signup/reset bursts can exhaust its daily allowance. Budget paid email for a dependable admission flow and cap abuse at the application. Verify the selected current volume tier: search results showed an alternate $35/100,000 tier, whereas the current price page explicitly lists $20/50,000. [Resend pricing](https://resend.com/pricing)

DigitalOcean blocks SMTP ports 25, 465 and 587. Resend documents 2465 for implicit TLS and 2587 for STARTTLS, which are candidate production-Supabase Auth delivery paths. Neither reachability nor Auth compatibility was tested. A configured SMTP secret alone is not delivery proof; test invitation, signup verification, reset and link expiry against the actual domain. Avoid introducing an unreviewed relay merely to evade a setup failure. [Droplet limits](https://docs.digitalocean.com/products/droplets/details/limits/), [Resend SMTP settings](https://resend.com/docs/send-with-smtp)

**Domain/TLS:** use an existing authorized domain/subdomain if available. The $2/month line is a $24/year planning allowance, not a quoted domain registration. Cloudflare Registrar sells at registry/ICANN cost; actual availability, TLD and renewal price remain unknown. TLS can use the production reverse proxy's automatic certificate management; test renewal and retain domain access recovery. [Cloudflare Registrar](https://www.cloudflare.com/products/registrar/)

**Maps:** Mapbox GL JS currently includes 50,000 map loads/month, then $5/1,000 for the next 50,000. Thus 60,000 loads would incur about $50 for that product alone. Geocoding, static exports, imagery and other APIs are separate meters. Do not equate visitors, page views and map loads. [Mapbox pricing](https://www.mapbox.com/pricing), [Map cost management](https://docs.mapbox.com/help/troubleshooting/manage-web-map-costs/)

Mapbox GL JS's current license depends on a valid Mapbox account and product terms; it is not covered by OpenPlan's Apache license. Its license restricts billing/telemetry interference. The legal page currently links July 21, 2026 Product Terms, but retrieval of that PDF failed here: this is not a complete current commercial-use/legal assessment. Keep Mapbox an explicitly configured provider with an authorized budget. A MapLibre alternative also needs lawful basemap tiles, styles, glyphs and data; replacing a renderer does not create a free hosted imagery service. [GL JS license](https://raw.githubusercontent.com/mapbox/mapbox-gl-js/main/LICENSE.txt), [Current product-terms landing page](https://www.mapbox.com/legal/product-terms)

**Other providers:** routing, geocoding, paid imagery and optional language-model services need per-provider meters and explicit funding, with a modest initially proposed $25–50 variable reserve. This is an allowance, not verified token or API pricing. Determine actual adapters, outbound payloads, licensing and billing before enabling them. A hosted preview cannot quietly substitute an API key from Nathaniel's development environment. Public-data downloads can be free at source and still consume worker time, disk and egress.

## Operation and acceptance work before calling it a functioning trial

These are proposed engineering acceptance conditions; none was executed in this research.

1. **Reproducible release and identity.** Install from an identified release on an empty isolated host; pin container/runtime versions, apply migrations, record app and worker source identities, and document recovery/configuration ownership. Demonstrate restart after host reboot. Use production server builds, not the development server or CLI Supabase exposed publicly.
2. **Network and trust boundaries.** Serve HTTPS; restrict database, Studio and worker control interfaces; protect deployment/backup credentials; prove workspace isolation through both UI/API and RLS. Trial tenants cannot see each other's uploads, private proposals, staff rates or exports. Public example data must be labeled and licensed; private trial data must not become demonstration data by default.
3. **Complete invited-user journey.** A planner outside the operator's network signs up or accepts an invite, logs in again, creates/edits project work, uploads and downloads evidence, performs supported analyses, requests long jobs, and exports results. Include desktop and 390px checks, console capture, actual mail delivery, and a second unrelated tenant. Record unsupported features honestly; a successful health endpoint is insufficient.
4. **Real worker operation.** Durable queue and authenticated dispatch, heartbeats, lease expiry, retries, idempotency, cancellation, disk/memory limits and result ownership. Interrupt a disposable job/worker and prove safe recovery without duplicated charges, writes or artifacts. Record both AequilibraE and ActivitySim independently; healthy workers do not establish method validity. Vercel's Pro function maximum of 800 seconds is not a durable large-job architecture. [Vercel function limits](https://vercel.com/docs/functions/limitations)
5. **Recovery across all durable state.** Establish a consistent recovery point for database rows, Auth state, Storage bytes, worker artifacts and protected configuration; restore on a different machine and verify object hashes, permissions and representative workflows. Propose initial RPO ≤24 hours and RTO ≤4 hours for discussion, then measure them; these are targets, not promises. Managed Supabase database backups omit Storage object bytes. [Supabase backup scope](https://supabase.com/docs/guides/platform/backups)
6. **Size from measured workloads.** Record idle/peak RAM, CPU, I/O, database connections, concurrent imports/exports, queue delay, object growth and provider billing units. Test progressively from one to several simultaneous planners rather than asserting capacity from RAM. Freeze representative jobs of increasing geography/data scale and measure each engine separately. An oversized job must be refused or queued with a clear explanation; it must not evict the database or silently truncate evidence.
7. **Budget enforcement and operator recovery.** Invite-only admission initially; workspace file/job quotas; bounded upload expansion, archive extraction, concurrency, runtime and retries; allowlisted fetch destinations and protections against SSRF; signed private downloads and limited exports; email throttles; provider-token restrictions. Prove that deliberately excessive requests are denied before expensive dispatch. Cost alerts are not spending stops. Supabase's spend cap excludes compute, branching, replicas and several add-ons. [Supabase cost controls](https://supabase.com/docs/guides/platform/cost-control)
8. **Human ownership and a sustained trial.** Name an operator and backup person, publish a support route and maintenance window, monitor external availability plus auth/storage/queue/backup age, and rehearse a bad deployment rollback. Run a proposed seven-day soak including a deploy, expired session, worker restart and restore drill. Ask agency and consultancy planners to complete actual work and identify missing steps. Preview availability is not a paid production SLA.

The current `openplan/docs/ops/BACKUP_AND_RESTORE.md` describes sequential `pg_dump` and Storage archive capture from explicitly named local CLI containers, plus a disposable restore drill. Those documented actions are not proof of scheduled hosted backups, atomic database/file consistency during concurrent writes, coverage of all external worker artifacts, or production Docker restoration. Snapshot backups and checksum-valid archives do not settle those gaps. The hosted work must adapt and prove the existing recovery approach rather than claim a new mechanism is already finished.

Allow roughly 2–6 operator hours/month for a small trial after stabilization as an explicit planning assumption, plus incident time; initial deployment/security/restore work is additional. This is not a labor quote. Managed infrastructure can reduce host/database chores but cannot take responsibility for OpenPlan tenant authorization, failed jobs, client data, procurement deadlines or scientific interpretation.

## Decision checkpoint and falsification

Before spending, produce a concrete bill of materials with exact region/SKU, tax treatment, monthly base, permitted variable ceiling, retention policy, owner and removal plan. Recommended first approval request: a limited invited trial with a **$200/month base-and-variable ceiling plus a separately stated model-worker allocation**, only after sizing work has narrowed uncertainty. If $200 must include a large continuously allocated worker, the proposed architecture does not fit and must be resized or scheduled honestly.

Reject or revise the VM recommendation if the production Supabase migration/auth flow fails, the operator cannot restore without the original machine, concurrent work causes unacceptable latency/OOM, or patches require unsustainable manual effort. Prefer managed infrastructure if it materially reduces that demonstrated operational burden within an approved budget. Reject the managed recommendation if long jobs depend on function lifetimes, essential artifacts depend on ephemeral filesystems, provider/network overhead exceeds the budget, or current application assumptions cannot be ported safely.

The remaining uncertainties are exact US bundled-plan stock, production configuration/migration compatibility, SMTP delivery, current Mapbox product-term applicability, complete provider inventory, realistic per-engine sizing, restore times/consistency, and trial support capacity. Each needs an identified record or later authorized test. No provider account, subscription, funding approval, working hosted OpenPlan deployment, or complete hosted acceptance evidence was established here.
