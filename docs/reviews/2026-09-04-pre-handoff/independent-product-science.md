# Independent scientific evidence review, 2026-09-04

This is a separate addendum. `independent-product.md` remains unchanged. The review used published reports, registries, comparison artifacts, loaders, verifier source, and selected worker/SQL code. It did not execute a model, run a verifier or test suite, access databases, open a holdout dataset, inspect frontend behavior, or change the checkout. The reviewed starting commit was `ad640ce7164cbea55bddd30341748e5f48639410`.

The present result is still scientifically inconclusive. The published v0.44 candidate is retired overall. Some county-method development gates passed, but none establishes model accuracy or authorizes a default change. The next science milestone should establish a reproducible, comparable development instrument and a defensible modeled quantity, then diagnose a specific structural correction. Acceptance requires a separate frozen protocol and evaluator; the current rules-v5 evaluator cannot return a scientific pass.

## Present scientific gaps

1. **There is no implemented v1 acceptance evaluator.** Rules-v5 initializes `outcome = "inconclusive"` and retains it even when a frozen rule exists, at `model_validation_core_v5.py:225-253`. This is appropriate for a diagnostic checkpoint. Adding a successor JSON with thresholds alone will not produce a valid acceptance gate. A separate versioned evaluator must implement the actual use, eligibility, interval treatment, coverage and stratum rules, and be tested before acceptance access.

2. **Model quantity, time and year remain unresolved.** Rules-v5 requires `synthetic_expanded_daily_traffic` and the exact representative peak-hour expansion chain at lines 61-87. Its comparability findings check model year, day, direction and vehicle basis at lines 150-170. Raw residuals are nevertheless available for diagnostic rows at lines 215-225. The v0.44 development gate computes residual medians directly from observation centers at `run_distributed_work_loading_study.py:685-717`; it does not turn those rows into decisive same-basis accuracy evidence. Treat improved diagnostic residuals as a reason to investigate, never as a claim of better AADT accuracy.

3. **Work endpoint distribution leaves major demand uncorrected.** LODES is job/home-work evidence. The source registry explicitly leaves non-work unchanged and retains missing-pair, unavailable, unmapped and unroutable states at `california_distributed_work_loading_study.v1.json:18-41`. Exact external and non-work through demand remain separate research/data needs. No scalar or gateway volume should be invented to absorb these gaps.

4. **Population synthesis is operational but not nationwide validated.** `scripts/modeling/synthetic_population.py:140-222` already fits real PUMS household seeds to zone controls and returns fit quality. `population_synthesis.py:29-40` retains unmet controls. Therefore 'we need a population synthesizer' is stale. The remaining questions include small-geography fit, uncontrolled joint distributions, sample limitations, person/household consistency, uncertainty, and geographic transfer. A successful fit to controls cannot establish travel behavior.

5. **ActivitySim's behavior and level-of-service representation remain limited.** The current MTC adapter repeats free-flow auto times across periods and disables transit alternatives through zero skims, at `scripts/modeling/activitysim_mtc_inputs.py:703-705,900-915`. `ACTIVITYSIM_RUNTIME_GAP.md:64-88` explains borrowed regional coefficients and screening-only interpretation. No transit forecast, congestion response, pricing/toll effect, or locally calibrated behavior is established by successful execution of this path.

6. **Geographic and use coverage is far short of the v1 claim.** These seven California development counties cannot establish all California archetypes, every state/DC, tribal contexts, or every published use. Baseline road counts alone also cannot validate build-response forecasts, mode choice, transit ridership, emissions, development impact, or environmental significance. Those uses need explicit observation and experimental designs. The contract requires them where claimed, not a blanket confidence label.

7. **Frozen runtime and current engine capability must remain separate.** The v0.44 verifier requires the frozen assignment version 1.6.2 at `verify_distributed_work_loading_study.py:147-150`. The current upstream documentation page now identifies AequilibraE 1.7.0. That is a reason to research a successor environment, not update installed dependencies underneath sealed comparisons. Any upgrade must receive new runtime custody and a controlled development comparison.

- The release verifier checks artifacts and the comparison's gate, but does not compare study-result per-method gate/coverage summaries to comparison objects at `verify_distributed_work_loading_study.py:151-158`. The SQL RPC does not invoke that validator. This is a source-established service-role RPC validation gap, not an authenticated-user bypass or a demonstrated database exploit. ## Official-source refresh and reuse decisions

AequilibraE already provides network editing, gravity/IPF distribution, skimming, traffic assignment and public transport assignment. Extend and test these existing capabilities before adding a new assignment system. Upstream functions are not evidence that OpenPlan has wired or validated them. The latest documentation page identifies 1.7.0, while the frozen v0.44 comparison remains 1.6.2. [AequilibraE Python documentation](https://www.aequilibrae.com/latest/python/index.html)

ActivitySim supports estimation data bundles and Larch-based submodel estimation. Its documented workflow uses household/person/tour/trip survey tables, model specifications, coefficients and alternatives together. This is a concrete existing path for local estimation or defensible transfer research. It does not supply a nationwide validated coefficient package automatically. The cited page is the upstream development documentation; match any implementation to a pinned release first. [ActivitySim estimation](https://activitysim.github.io/activitysim/develop/estimation.html)

PopulationSim is an existing open population synthesis tool using seeds and controls. Its own validation guidance warns that regional control fit does not reveal lower-geography fit adequately. Use it as an independent development comparator against OpenPlan's existing synthesizer before considering replacement. Require a measured advantage and preserve provenance; do not restart closed population-generation work because an old document calls it missing. [PopulationSim introduction](https://activitysim.github.io/populationsim/), [PopulationSim validation](https://activitysim.github.io/populationsim/validation.html)

The current LODES 8.4 technical document confirms that state main files cover jobs with workplace and residence in-state, while auxiliary files cover workplaces in-state with residence outside. Thus California files alone do not cover California residents' out-of-state jobs. The fields count jobs, and the documentation says Puerto Rico is not included because of data infrastructure constraints. A later nationwide adapter must register the required workplace states and retain unsupported territories, without treating jobs as daily vehicle trips. [Census LODES 8.4 technical documentation](https://lehd.ces.census.gov/data/lodes/LODES8/LODESTechDoc8.4.pdf)

`OPEN_SOURCE_MODEL_LANDSCAPE.md:30-37` rejects MATSim partly because of a six-minute screening target, and lines 74-76 still call synthetic population generation the biggest blocker. Those assumptions conflict with the current no-runtime-ceiling contract and existing synthesis. Supersede those reasons in a new dated review. This does not justify replacing the required AequilibraE/ActivitySim methods; it means evaluating supplementary dynamic tools against an actual unsupported use instead of a stale runtime preference.
