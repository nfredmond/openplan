# ODM and WebODM feature benchmark for OpenPlan

Research date: 2026-09-04. This is a source-backed benchmark and evaluation proposal, not a live competitor comparison or an implemented OpenPlan capability claim. No application, drone, processing engine, browser journey, account, database or test was operated. Only this report was written.

## Current identity and source inventory

WebODM is now an independent project. Its creator announced separation on April 6, 2026, identifying ODX and NodeODX as forks of ODM and NodeODM. Current WebODM documentation identifies ODX, MicMac and LGT as supported processing engines. Therefore “WebODM is just ODM’s UI” is an obsolete description of the current relationship. [Official separation announcement](https://webodm.org/blog/announcement/), [current documentation](https://docs.webodm.org/).

OpenDroneMap continues to publish ODM, NodeODM, PyODM and ClusterODM. WebODM publishes the parallel ODX/NodeODX ecosystem and its own application. Keep engine, API adapter, processing job, viewer and planning record distinct when selecting reuse. [OpenDroneMap ecosystem](https://opendronemap.org/), [WebODM ecosystem](https://webodm.org/).

Inventory preceded detailed reading: official homepages and announcement; official documentation navigation; default-branch repository identities/licenses; selected engine argument definitions; task/permission/recovery documentation; GCP, multispectral, elevation, 3D, stockpile and large-dataset tutorials; selected contour/volume source. No release binaries, imagery datasets, container images or full repositories were downloaded.

## Substantial feature benchmark

This is the full substantial baseline to retain, not a shortlist for the first demonstration. “Documented” means a current primary source describes the capability; “source” means the sampled pinned code exposes it. Neither means this reviewer operated it. OpenPlan completion must track every family, including unproved interim states, and cannot close on one successful orthophoto.

For common engine features, both pinned [ODM argument definitions](https://github.com/OpenDroneMap/ODM/blob/69ca6212ca2f885b41cee6bb19d32f6ddecf79bc/opendm/config.py) and [ODX argument definitions](https://github.com/WebODM/ODX/blob/eb9fd56ac430fc3735401d88aaef9945ebd00e14/opendm/config.py) were sampled. They expose camera models, radiometric calibration, GCP/geolocation, alignment, DSM/DTM, classification, tiled outputs, split processing and rerun controls. Those options do not establish equivalent numerical results or identical WebODM UI behavior.

| Family | Current documented/source baseline | Planning meaning and required verification |
|---|---|---|
| Input and capture types | WebODM describes JPEG/TIFF, 8/16-bit imagery, geotagged or not, standard/fisheye/360 cameras and aerial/ground, nadir/oblique capture. [Features](https://webodm.org/) | Preserve actual sensor, band, bit depth, image identity and capture geometry. Reject unsupported variants clearly. Test mixed/duplicate/corrupt imagery, orientation and missing metadata. A supported extension does not prove a supported camera workflow. |
| Video-derived imagery | Both pinned engine READMEs describe frame extraction from MP4/MOV/LRV/TS and matching GPS SRT files. [ODM README](https://github.com/OpenDroneMap/ODM/blob/69ca6212ca2f885b41cee6bb19d32f6ddecf79bc/README.md#video-support), [ODX README](https://github.com/WebODM/ODX/blob/eb9fd56ac430fc3735401d88aaef9945ebd00e14/README.md#video-support) | Preserve source video, time/frame selection and telemetry correspondence. Evaluate blurred or redundant frames and absent telemetry. Do not label frame extraction a different proven reconstruction method. |
| Camera and processing controls | Both engines expose calibration, lens, rolling-shutter, feature/cloud quality, concurrency and output-resolution settings. WebODM supplies processing options/presets. [ODX options](https://docs.webodm.org/options-flags/) | Record actual engine/settings and why the capture supports the intended output. Compare settings on development data; do not silently change a reviewed job to make it pass. |
| GCP and RTK/georeferencing | WebODM documents CRS-aware GCP files, visual marking, EXIF choice and `force-gps` for combining precise image positions with GCPs. [GCP documentation](https://docs.webodm.org/ground-control-points/) | Preserve measured coordinates, horizontal/vertical reference, precision, marked pixels and processing use. RTK is positioning evidence, not automatic accuracy certification. Raw GNSS/PPK processing completeness is unverified here. |
| Independent accuracy checkpoints and QC | Current GCP documentation distinguishes `CHK-` points excluded from reconstruction for accuracy checking. ODX README advertises checkpoint support; both engines expose PDF reporting controls. [GCP documentation](https://docs.webodm.org/ground-control-points/), [ODX README](https://github.com/WebODM/ODX/blob/eb9fd56ac430fc3735401d88aaef9945ebd00e14/README.md) | Freeze control versus check roles before results, retain residuals and spatial coverage, and independently inspect QC output. GCP fit is not independent validation. ODM’s exact checkpoint convention was not established by the sampled options. |
| Orthophotos and map inspection | Georeferenced orthomosaics, resolution controls, map viewing and GeoTIFF outputs are documented; quality depends on parameters/capture. [Orthophoto tutorial](https://docs.webodm.org/tutorials/creating-high-quality-orthophotos/) | Inspect coverage gaps, seams, tilted structures, units and source date against control and the intended scale. Smaller output pixels do not establish more measured detail. |
| Point clouds, DSM and DTM | Both engines expose classification and DEM options. WebODM’s DTM uses ground classification; its tutorial warns of misclassification and interpolation effects. [DEM tutorial](https://docs.webodm.org/tutorials/creating-digital-elevation-models/) | Distinguish visible surface from estimated terrain. Review canopy/buildings/steep ground, voids and interpolation before slope, drainage, accessibility or earthwork claims. Photogrammetric ground filtering is not evidence that the camera saw through vegetation. |
| 3D inspection and annotations | WebODM’s Potree documentation includes source-camera/image inspection, textured models, point budgets, clipping, navigation, coordinates, distances, heights, angles, profiles and annotations. [3D viewer](https://docs.webodm.org/tutorials/potree-3d-viewer/) | A planner can inspect an actual location and trace it to source imagery, save a review note and hand off a readable figure. Verify measurements separately from rendering quality and provide usable non-3D alternatives where needed. |
| Area, length and stockpile volume | WebODM documents map measurements and stockpile base selection. Pinned volume code implements triangulated, planar and other bases, converts volume units, and returns absolute net volume. [Stockpile tutorial](https://docs.webodm.org/tutorials/measuring-stockpile-volume/), [volume source](https://github.com/WebODM/WebODM/blob/86c4735b19b07605a9a3c1e9e708bdbccf8b80a0/coreplugins/measure/volume.py) | Preserve geometry, selected surface and base method. Independently recompute. Do not treat an absolute net volume as separately measured cut/fill or an approved pay quantity; mixed positive/negative changes can cancel before absolute value. No runtime error claim is made here. |
| Contours and CAD/GIS handoff | Pinned contour code supports DSM/DTM, interval, crop, simplification, units and GPKG, Shapefile, DXF and GeoJSON export. [Contour source](https://github.com/WebODM/WebODM/blob/86c4735b19b07605a9a3c1e9e708bdbccf8b80a0/coreplugins/contours/api.py) | Reopen in independent GIS/CAD; verify levels, horizontal/vertical units, feature coverage, simplification and source DEM. A contour interval is not an accuracy statement. |
| Repeat surveys and change | Both engine configurations contain alignment; WebODM documents aligning later tasks to a prior point cloud/DEM. [Temporal alignment](https://docs.webodm.org/ground-control-points/#multi-temporal-datasets) | Require stable reference areas, compatible dates/datums and uncertainty before describing change. Alignment can move/scale a reconstruction; it does not by itself distinguish construction change from registration error. Full automated statistically defensible change detection was not established. |
| Multispectral and thermal | WebODM documents reflectance/temperature orthophotos, band alignment and sensor-specific radiometric processing. Some thermal inputs require external preprocessing. [Multispectral/thermal](https://docs.webodm.org/multispectral/) | Preserve bands, calibration, units, illumination and sensor metadata. Compare vegetation/heat questions only where actual observations support them. A color index is not a validated species, health or regulatory conclusion; external-tool license/availability must be resolved. |
| Photorealistic splats | WebODM documents exporting training data, processing in external software such as OpenSplat and importing a splat for display. Nadir-only capture is discouraged. [Splats workflow](https://docs.webodm.org/gaussian-splats/) | Retain the workflow in the full benchmark, with actual input/output handoff and display. Attractive visualization cannot certify measured geometry, quantities or engineering fitness. This is not proven one-click in-app training. |
| Task lifecycle and recovery | WebODM exposes queue/run/failure/completion/cancel states, pending actions, logs, progress, available assets and possible rerun stages. An empty rerun-stage list means start again. [Task API](https://docs.webodm.org/api/task/) | Preserve the distinction between accepted request, running job, produced bytes and validated output. Exercise reconnect/restart and missing intermediate files. Engine rerun stages and independent survey checkpoints are unrelated concepts. |
| Large jobs and distribution | Local split/merge and distributed NodeODX/ClusterODX processing are documented. Current tutorial says textured meshes are not merged; submodels with fewer than three GCPs fall back to remaining controls plus EXIF. [Large datasets](https://docs.webodm.org/tutorials/large-datasets/) | Inspect split boundaries and every deliverable, not just a merged thumbnail. Disclose changed georeferencing and unsupported merged meshes. Parallelism must preserve job/source identity and avoid double publication. No cloud autoscaler is required by this review. |
| GPU and resource controls | Both engines document GPU support; their advertised accelerated stages differ. [ODM GPU](https://github.com/OpenDroneMap/ODM/blob/69ca6212ca2f885b41cee6bb19d32f6ddecf79bc/README.md#gpu-acceleration), [ODX GPU](https://github.com/WebODM/ODX/blob/eb9fd56ac430fc3735401d88aaef9945ebd00e14/README.md#gpu-acceleration) | Measure actual end-to-end time, memory, scratch storage, GPU use and output quality on the selected hardware. An accelerated stage does not prove a proportionate job speedup or superiority over the other engine. |
| Offline and team deployment | WebODM advertises local/offline processing; installation docs distinguish processing resources from the lighter UI. [Product](https://webodm.org/), [installation](https://docs.webodm.org/installation/) | Test a real disconnected workflow with needed files/software already present, and separately a self-hosted team installation. Identify external basemap, geoid, license, update and auxiliary-service dependencies rather than assuming “offline” covers everything. |
| Sharing and permissions | WebODM documents sharing and object/model permissions; tasks inherit project permissions. [Permissions](https://docs.webodm.org/api/permissions/), [task API](https://docs.webodm.org/api/task/) | Verify internal reviewer, consultant, public derivative and revoked recipient access, including original photos/location metadata. A share link is not agency authorization to publish. Basic permissions existing upstream must not be described as absent. |
| Export, transfer and recovery artifacts | Documented outputs include GeoTIFF/PNG, LAS/LAZ, OBJ/3D Tiles; options include COG, COPC/EPT and CSV. Task import/download and a backup endpoint are documented. [Features](https://webodm.org/), [options](https://docs.webodm.org/options-flags/), [backup](https://docs.webodm.org/api/reference/operations/projects_tasks_backup_list/) | Independently reopen full-resolution outputs with CRS/units/metadata. Prove source, measurement and review preservation through transfer/restore. A downloadable task backup does not establish full installation recovery or that every source/intermediate is included. |
| Extensibility and operator features | WebODM has a documented plugin system. Pinned core-plugin inventory includes contours, measure, GCP editing, snapshots, notifications, task manager, shortlinks, diagnostic, object-detection and external-service integrations. [Plugin guide](https://docs.webodm.org/plugin-development-guide/), [pinned core plugins](https://github.com/WebODM/WebODM/tree/86c4735b19b07605a9a3c1e9e708bdbccf8b80a0/coreplugins) | Classify substantial enabled features, optional integrations and examples separately. A directory name is not feature acceptance. Preserve localization, branding and administrative usability in evaluation; do not install every plugin or assume its service is free. |
| Mission preparation and flight handoff | WebODM explicitly says it has no official mission planner yet and points to third-party tools. [Mission-planning documentation](https://docs.webodm.org/mission-planning/) | OpenPlan’s full mission/AOI/flight-export direction can add value, but supported flight-app/drone compatibility and operator decisions need their own proof. Root and the separate DJI researcher own that integration review. |

## Source limitations that should change product decisions

The official GCP guide advises replacing an unknown/NaN elevation with `0.0` to avoid processing trouble. **Do not copy that into OpenPlan as a measured elevation.** Preserve missingness, require a valid control workflow, or explicitly represent an unsupported/assumed input with its actual meaning. The same guide contains broad GSD-based accuracy heuristics and use-case examples; these do not establish accuracy for a new job. No universal “survey-grade” threshold is adopted here. [GCP guide](https://docs.webodm.org/ground-control-points/).

The direct WebODM installation guidance recommends 16 GB RAM and 100 GB free disk for a standalone processing installation, with conservative examples of 250 images at 16 GB and 500 at 32 GB. These are source estimates, not measured OpenPlan limits or guarantees; image dimensions, options and concurrency matter. Budget source photos, intermediate reconstructions, derivatives, backups and simultaneous jobs separately. [Hardware requirements](https://docs.webodm.org/installation/#hardware-requirements).

WebODM’s current home page says ODX is faster than ODM. That is the project’s claim, not this review’s comparative finding. Official documentation also retains some inherited naming and older examples. Pin the actual tested engine/API combination, capability discovery and artifacts; do not use branding or a CLI flag alone as proof of compatibility.

## What could be better for planning

OpenPlan should retain the full substantial baseline above and improve the complete planning job. These are proposed outcomes, not findings that WebODM lacks every corresponding feature.

- A small-town planner starts with a project, purpose, study area and required accuracy, hands a supported capture plan to an operator, reviews the reconstruction and produces a source-bound corridor or land-use exhibit. There is no repeated project/geography entry between mission, files, map and report.
- A capital-project reviewer compares permitted surveys over time, records alignment and measurement choices, and links a reviewed quantity to a work item. Approved payment remains separate from a computed volume. The reviewer can reconstruct the conclusion after staff turnover.
- A resilience, vegetation or heat study uses the appropriate surface/band/calibration evidence and records what cannot be inferred. Maps, narrative and public figures preserve the same source version and uncertainty.
- An agency releases a selected map/3D derivative with understandable limitations and an accessible alternative, while protecting sensitive original images and coordinates. Engagement responses can reference the exact approved exhibit.
- A grant or plan author reuses an approved image, contour or measurement with its source, quality and permissions intact. Updated imagery reopens affected current conclusions without rewriting previously adopted evidence.

Existing Aerial, processing workers, Documents, Projects, GIS, Reports, Grants and Engagement are the intended homes. The current whole-product contract names aerial evidence in the shared spine at `docs/product/V1_PRODUCT_CONTRACT.md:162–169`; the current draft’s M5b restores the full ODM lane. This benchmark does not audit current OpenPlan code or infer absence from a single file. Root owns that comparison. The useful distinction is a complete planning record around a capable processing/inspection workflow, not merely placing a new front end over a smaller subset of engine functions.

## Reuse and staged completion

First preserve a feature-to-output-to-acceptance matrix using the families above, with exact engine/API/version, supported input/sensor, user entry point, artifact, license status and evidence state. “Unsupported” is an honest interim status, not grounds to delete a required substantial capability. Refresh the matrix when either upstream changes.

Evaluate the current OpenPlan worker/API contract against ODM/NodeODM and ODX/NodeODX using bounded fixtures and then permitted real jobs. Reuse established photogrammetry, geospatial and 3D components where they meet the requirement. Choose a coherent supported baseline after compatibility, quality and licensing review; do not deploy both stacks merely because both exist. A switch to ODX is a reviewed engineering choice, not a silent renaming of a pinned ODM result. Preserve engine provenance and old artifacts.

Deliver complete increments within M5b: capture/input/control records; processing and honest task recovery; full 2D/3D inspection, measurement and export; multispectral/thermal and repeated surveys; large-job/team/offline operation; connected planning/approval/public handoff. Each increment needs its own proof. An early useful RGB orthophoto case can validate a narrow stage while all unfinished feature families remain open. It cannot satisfy the user’s full benchmark ambition.

## Evaluation needed before a superiority claim

Use separate experiments for reconstruction quality, operational reliability and planner usefulness. Comparing OpenPlan with WebODM while both call the same engine cannot establish a better reconstruction algorithm; it may establish a better planning workflow.

Before evaluation, freeze the datasets, control/check separation, processing settings, hardware, output requirements, quality criteria and measurement procedure. Include urban/corridor detail, rural terrain, oblique structures, vegetation/occlusion, repeat-survey alignment, a relevant multispectral/thermal dataset and a job large enough to exercise splitting. Use permitted real observations and independent checks appropriate to each intended use. Do not tune on the acceptance checkpoints, erase failed submodels or substitute a smaller dataset after seeing difficulty. Set use-specific tolerances with the responsible practitioner from authoritative standards and needs; no numerical threshold is invented here.

Measure completeness and positional/vertical error against independent checks, visible reconstruction defects, quantity differences, required artifact validity, runtime, peak RAM/VRAM, scratch/output/backup size, failed/recovered work and operator interventions. Record uncertainty and engine disagreement rather than selecting only the flattering outputs. Test loss of the UI connection, worker interruption, exhausted disk, missing source/asset, duplicate upload, changed GCP, unavailable processing node and restore onto a separate installation. Recovery must preserve the actual state and owner’s work.

For human usefulness, practicing planners and a qualified imagery/GIS operator complete matched tasks in current, identified WebODM and OpenPlan environments. Include setup, control marking, inspection, correction, exports, report reuse and a real recipient’s review, not just processing time. Counterbalance task order and predefine acceptable errors and improvement criteria. Measure total time including corrections, lost context/re-entry, mistaken accuracy interpretation, successful handoff and independent repeatability. Observe keyboard/touch/accessibility, constrained connectivity and public/private comprehension. Document competitor version and access limits. No live comparative evidence was collected here.

Completion requires full substantial feature coverage plus the selected planning improvements, valid artifacts and independent review. A green worker exit, a pretty point cloud, an export button or a source feature list does not establish that outcome.
