## Finding and recommendation

Nathaniel’s reference directly matches the requested architecture. T3 Code controls agents executing on the environment that owns their installed binaries, credentials, configuration and files. Its README explicitly describes installed/authenticated Codex, Claude Code and OpenCode and subscription use. Source confirms substantive adapters for all three, with events, approval requests, persistent sessions, cancellation and recovery. The README’s subscription claim does not independently establish entitlement for every provider, plan or sharing arrangement; actual provider requirements belong in the accompanying official-provider review. [README](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/README.md), [architecture](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/internals/overview.md).

Extend OpenPlan’s existing Planner Agent with a local companion, provider adapters, and one planning-action contract shared by API and CLI routes. Reuse T3’s protocol/lifecycle work where practical. Do not fork its whole coding editor or inherit its host-level permissions as authorization for agency records.

## Reusable decisions

1. **Provider kind differs from configured instance.** T3 isolates each instance’s account/configuration lifecycle, adapter, catalog and generation state. OpenPlan should bind a session to user, workspace, project, provider instance and execution environment, not route by model name alone. [Driver contract](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/ProviderDriver.ts).
2. **Normalize lifecycle at the boundary.** Common operations cover start/send/interrupt/approval/question/stop/list/read/rollback and normalized events. Capabilities distinguish in-session model switching, promptless continuation and rollback. Preserve unsupported states rather than silently approximating them. [Adapter contract](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/Services/ProviderAdapter.ts).
3. **Persist intent before effects.** T3 documents transactional events/projections/command receipt followed by side-effect reactors. Command acknowledgment differs from work completion. Apply this principle to OpenPlan’s existing durable jobs/action ledger; adopting T3’s entire event engine needs separate justification. [Architecture](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/internals/overview.md).
4. **Execution stays with its owner.** Browser/mobile clients connect to the execution environment; credentials and processes stay there. A changed transport does not change ownership, and cleanup must stop only owned processes. This supports a planner using a personal installed CLI while accessing the UI elsewhere. [Remote architecture](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/internals/remote.md).
5. **Every transport method declares authority.** T3’s RPC type map requires a scope for every method. OpenPlan needs this completeness mechanism plus resource-level planning authorization; socket authentication alone is insufficient. [RPC map](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/auth/RpcAuthorization.ts).
6. **Narrow planning-tool bridge.** T3 injects a thread-specific authenticated MCP connection. This is a useful seam for OpenPlan’s existing typed actions: inspectable proposal, exact payload approval and server-side permission checks, rather than direct model database access or guessed endpoints. [MCP session](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/mcp/McpProviderSession.ts), [Claude injection](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/Layers/ClaudeAdapter.ts#L4549).

## Important differences OpenPlan must preserve

T3 defaults new threads to Full access. Claude maps that to `bypassPermissions` and `allowDangerouslySkipPermissions`; OpenCode allows all tools/external directories. Those are coding-product decisions, unsuitable defaults for publishing engagement findings, adopting a plan or issuing an invoice. OpenPlan’s exact planning-action authorization must remain enforced even if the underlying CLI has broad permissions. [Permission guide](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/user/permission-modes.md), [Claude runtime options](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/Layers/ClaudeAdapter.ts#L4539), [OpenCode permission rules](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/opencodeRuntime.ts#L480).

T3 expressly describes projects as organizational boundaries, not filesystem sandboxes; its read scope includes host-readable absolute paths outside a project. OpenPlan has stronger workspace/confidential-record requirements. Recommended companion scope: selected project directory and evidence, scoped tools, no service-role database credential exposed to the model, no automatic whole-home context ingestion, and disclosure of which records leave the machine. Native CLI permission modes supplement rather than replace OpenPlan authorization. [Environment authentication](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/internals/environment-auth.md).

T3’s Codex guide includes `/feedback` uploading conversation and logs to OpenAI. Any reused equivalent must remain explicit and inspectable because planning records can contain participant, property and procurement information. T3’s feature does not authorize exporting OpenPlan records. [Feedback guide](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/user/providers-codex.md).

Do not promise arbitrary provider switching preserves native conversation semantics. T3 exposes switching/rollback capabilities and separate native account homes. A changed backend may require a new session with an explicit selected-evidence summary. [Capabilities](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/Services/ProviderAdapter.ts), [Codex homes](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/user/providers-codex.md), [Claude homes](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/user/providers-claude.md).

## Tests worth adapting

Relevant tests cover Claude approval correlation, interrupted results and live-task cancellation; OpenCode resume, transport/auth errors not silently creating a fresh session, permission timeout retry, reconnect recovery, concurrent starts, child cancellation and late events after interruption. The sampled OpenCode permission tests cover unknown tools, network access and environment-file reads; their helper approximates native rule matching. These are useful deterministic examples, not proof that an installed provider version enforces the same behavior. No suite was run here. [Claude approval test](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/Layers/ClaudeAdapter.test.ts#L4612), [OpenCode adapter tests](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/Layers/OpenCodeAdapter.test.ts), [OpenCode permission tests](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/opencodeRuntime.permissions.test.ts), [Codex tests](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/apps/server/src/provider/Layers/CodexAdapter.test.ts).

OpenPlan acceptance must include missing binary/version, signed-out CLI, unavailable model, quota exhaustion without paid-API fallback, stop/restart/disconnect, accepted-command versus completed-action status, duplicate delivery, expired/wrong-workspace token, changed payload after approval, hostile instructions in imported comments and out-of-scope filesystem attempts. A harmless mutation must survive while removed authorization/payload binding fail. After isolated development, exercise a real authorized session for each supported CLI plus deterministic protocol fixtures in CI. API and CLI routes should produce the same traceable planning artifact and approval behavior.

## Roadmap definition

Initial milestone: visible **Use my installed agent** setup within the existing Planner Agent alongside API settings. Show backend, detected version, native auth/account state where available, models, execution machine and session status. Installation/sign-in remain explicit user actions. Opening settings should not launch login, tools or billable model work; T3 warns session probes may start hooks/MCP/authentication. [Provider constraints](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/internals/providers.md), [installation](https://github.com/pingdotgg/t3code/blob/b906ce2d73d025e801877f42a35b7a2f5629806f/docs/user/install.md).

Done means the user can complete the same bounded planning task with API and supported installed CLIs, inspect sources/proposed changes, approve an exact change, stop/resume safely and recover without duplicate mutations. Provider extensibility must retain explicit tool/structured-output/approval capabilities and unsupported states. Arbitrary model choice does not establish universal tool support or subscription entitlement.
