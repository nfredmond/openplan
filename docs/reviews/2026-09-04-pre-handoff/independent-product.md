# Independent OpenPlan product-direction review, 2026-09-04

Reviewer: independent product reviewer. Reviewed commit `ad640ce7164cbea55bddd30341748e5f48639410`, package v0.44.0. This report was written before reading any sibling review. Its conclusions are independent recommendations, not adopted product decisions.

OpenPlan needs a complete planning record that a second agency can understand and use. The current code has much of that record, but geography, legal authority, plan type, and export meaning still change at module boundaries. Repairing those relationships has more immediate product value than adding another specialist page. Nationwide scientific validation remains mandatory and must continue as its own program.

The most consequential findings are concrete. Land-use legal bundles are checked against the workspace's home state rather than the plan's governing authority. California general and specific plans receive the same legal checklist. The installation guide calls Docker Desktop free even though Docker requires government entities to buy a subscription. These undermine ordinary consultancy, agency, and California use before the more ambitious nationwide promise is considered.

## Findings that should change direction

### 1. A workspace is not the governing jurisdiction of every plan it contains

`openplan/src/app/api/land-use-plans/route.ts:22-29` accepts an authority label, geography label, and arbitrary object for GeoJSON. At lines 74-95 it checks the configured descriptor against `workspaces` home jurisdiction. At lines 105-107 it saves the independently supplied plan labels and geometry. `openplan/src/lib/land-use-plans/registry.ts:221-264` explicitly selects bundles from workspace jurisdiction. `openplan/src/components/land-use-plans/land-use-plan-creator.tsx:18-31` explains this workspace-based recommendation to the planner.

The code therefore rejects a California client plan in an Oregon consultancy workspace. Conversely, the route's jurisdiction guard does not establish that an Oregon plan drawn inside a California workspace is governed by California law. The latter is a code-level gap, not a claim that a browser or database reproduction succeeded. The sampled test checks Puerto Rico workspace refusal and database failure, not independent plan jurisdiction, at `openplan/src/test/land-use-plan-create-jurisdiction.test.ts:42-89`.

This matters to multi-client consultants, multistate MPOs, tribal governments, and state agencies with overlapping authorities. A polygon locates the study; it does not establish which government may adopt a plan or which legal regime governs an action. The existing neutral default is sensible, but workspace location must not become legal proof.

Extend the existing place representation rather than create another geography stack. `openplan/src/lib/geographies/place-of-record.ts:1-17` already anticipates plans as another owner. Preserve distinct concepts: workspace home, exact study geometry, sourced jurisdiction identities, governing authority, applicable legal bundle and version, and the human determination of applicability. Multiple jurisdictions and sovereign authorities must be representable without pretending that one state code decides everything. Unset or conflicting applicability remains explicit.

### 2. California plan kinds need different requirements

The configured descriptor offers General plan and Specific plan at `openplan/src/lib/land-use-plans/registry.ts:70-73`, but a shared required element list follows at lines 74-104. The create route seeds all required descriptor sections without plan-kind filtering at `openplan/src/app/api/land-use-plans/route.ts:117-147`. The shared process includes a generally-four-amendments notice at registry line 123.

California Government Code 65451 requires specific-plan content about land use, infrastructure, development criteria, implementation and financing, plus its relationship to the general plan. Section 65453 allows a specific plan to be amended as often as the legislative body deems necessary. Those differ materially from a general-plan checklist and amendment-frequency notice. This is current primary-source evidence, not an inference from the existing descriptor. [California Legislature, specific plans](https://leginfo.legislature.ca.gov/faces/codes_displayText.xhtml?article=8.&chapter=3.&division=1.&lawCode=GOV&part=&title=7.)

Add plan-kind applicability to content and process rules. Do not fix this with another broad disclaimer. Also examine the shared public-draft gate: `openplan/src/lib/land-use-plans/workflow.ts:59-82` requires a mapped designation and an implementation action for every public draft. These may be useful product defaults, but their universal suitability for a text-only amendment or an early review round is unproven. Separate the agency's chosen workflow prerequisites from statutory requirements.

### 3. Import and export names overstate what travels

The workbook contract exports place source, kind, reference, country, subdivision, source-document identity, and timestamps, but its automatic import mapping stops at source-location text. See `openplan/src/lib/projects/portfolio-round-trip-contract.ts:6-39`. Import explicitly never updates an existing same-name project at `openplan/src/lib/projects/portfolio-import.ts:881-892`; the commit payload carries the mapped values at `openplan/src/app/api/projects/import/route.ts:267-288`. Thus the current round trip is a reviewed creation path preserving selected values, not an edit/reconcile round trip of a project record. Exported place identity is not automatically restored by this mapping. That conservative behavior may be deliberate and safe, but a planner needs the exact meaning before editing a workbook and expecting it to update the project.

GeoPackage has a similar seam. The builder accepts separate model-link and designation layers at `openplan/src/lib/projects/project-geopackage.ts:604-644`. The direct download calls it with project and corridors only at `openplan/src/app/api/projects/[projectId]/export/geopackage/route.ts:101-107`. The other production call, `openplan/src/lib/project-evidence-bundles/generated-records.ts:391-397`, adds crash and approved engagement geometry, but still does not supply model-link or land-use designation layers. A search of production call sites found those two calls only. Model/designation geometry support is therefore not connected to those production exports. Layer-status disclosure is good, but it does not complete the handoff.

Use one evidence-selection and assembly path for direct download and governed handoff, with explicit differences in selection and permissions. Give recipients stable IDs, units, geometry/CRS, source vintage, layer coverage, claim limits, and separate model methods. Validate reuse in QGIS and a second OpenPlan workspace, not just successful file creation. QGIS has native GeoPackage metadata support, so an established open tool is already available for the recipient check. [QGIS metadata tools](https://doc.qgis.org/testing/en/docs/user_manual/introduction/general_tools.html)

### 4. Free agency installation is contradicted by the recommended desktop dependency

`README.md:79-119` calls the prerequisites two free programs and directs Windows/macOS users to Docker Desktop. Docker's current documentation states that government entities require a paid subscription. The Linux Docker Engine path at `README.md:125-139` is materially different. [Docker Desktop license](https://docs.docker.com/subscription/desktop-license/)

Fix the claim immediately, then prove a free supported installation path for the agency user. A Linux host with browser clients is a plausible existing route. A free Windows/macOS container alternative needs its own compatibility and stranger-install evidence before recommendation. Do not provision anything paid or imply that OpenPlan's open-source license exempts an agency from another product's terms.

`README.md:71-72` also states that nothing is sent anywhere. Configurable external model calls exist in `openplan/src/lib/integrations/anthropic-access.ts:19-49`, and the setup requires an external map token at README lines 234-239. Replace the absolute privacy statement with a clear account of local storage and enabled outbound services. This review did not inspect network traffic or establish a data leak.

### 5. The documented gap register sometimes closes the diagnosis instead of the defect

`docs/ops/KNOWN_ISSUES.md:53-54` places unknown demand provenance and disconnected/unloaded network defects under Closed in v0.37.0, although the resolution describes v0.43 diagnoses and says correction and untouched validation remain future work. Diagnosis is valuable, but the underlying defect remains open. Preserve dated evidence and distinguish disclosure fixed, diagnosis completed, and behavior corrected. Otherwise future agents can read a closed row as permission to claim the problem is gone.

The product already has a useful foundation for this distinction. The v0.44 loader requires `scientificOutcome: "inconclusive"`, separate methods, and fourteen records at `openplan/src/lib/models/published-distributed-work-loading.ts:38-44,72-86`. Do not weaken that boundary while making the status system easier to read.

## The ten required answers

1. **What would make this the ultimate free planning operating system?** A planner should bring an existing job, agency rules, data, and documents; define the actual decision; evaluate alternatives; record public and technical review; obtain the responsible approval; publish a usable artifact; and carry the decision into implementation. Another agency should be able to accept the record without reconstructing it. Every consequential value must retain source, date, geography, units, uncertainty, version, and permitted use. The job must survive staff turnover, an interrupted worker, and an upgrade. This applies to all 50 states and DC, with California depth and separate validated AequilibraE and ActivitySim results. It does not require OpenPlan to reimplement every GIS, word processor, or model engine.

2. **Can every kind of US planner do their core work?** No. The foundations are broad, but a module name or work-plan template is not a completed practice. The table below lists source-backed foundations and open jobs. Proposed missing jobs are priorities to test against actual planner work, not a claim that every row needs a new module.

| Practice and existing home | Foundation sampled or inventoried | Shallow, missing, or unproven job |
|---|---|---|
| Long-range and regional planning: RTP, Plans, Projects, Programs | RTP chapter/extraction/export routes; public comments already join to cycles through `lib/rtp/comment-response.ts:14-51` | Complete cycle from adopted prior plan through assumptions, fiscal choices, public response, amendment, and successor adoption; statewide and multistate responsibilities |
| Comprehensive, community, housing, and land-use planning: Land Use Plans and Data Hub | Frozen versions, reviews, decisions, designations, implementation in `lib/land-use-plans/contracts.ts:27-153` | Correct plan-kind law, parcel-level housing capacity and site inventory, zoning/plan consistency, housing review submissions, amendments that preserve parent-plan authority |
| Development review: Projects plus Land Use Plans | Project controls and plan implementation links | Intake and completeness, applicant revisions, referral responses, findings tied to applicable policies, conditions of approval, appeal/effective dates, inspections or implementation closeout; no complete case workflow identified |

Housing is a particularly concrete next depth test. HCD requires parcel/site inventory and electronic submission using its standards; a generic housing section plus a work-plan deliverable does not do that job. Existing source inputs and forms should guide an extension of Land Use Plans and Data Hub. [HCD sites inventory](https://www.hcd.ca.gov/housing-element/sites-inventory)

3. **Does every state work in substance?** No evidence establishes that. The live source registers only California and neutral land-use descriptors as selectable at `registry.ts:203-205`. Washington, Texas, and tribal descriptors are explicitly fixtures, not configured bundles, at lines 131-200. The grants registry has a federal bundle plus six state bundles at `lib/grants/programs/registry.ts:14-32`; that is not full state coverage. Jurisdiction readiness refuses unknown or missing subdivision/cells at `lib/jurisdiction-readiness/registry.ts:64-115`, which is honest degradation. The documented state ledger marks no state proven at `US_PLANNING_CAPABILITY_MATRIX.md:91-111`. All 50 states/DC still require actual jobs, sources, agencies, artifacts, and applicable law, not one nationwide display test.

4. **Is California the gold standard across its diversity?** No. It has the deepest configured descriptor, but the plan-kind mismatch is already a counterexample. Housing site analysis, specific-plan production, coastal and tribal applicability, rural staffing, county/city differences, and statewide agency work need explicit journeys. California remains partial; a county model demonstration or one local plan cannot represent all those contexts. Do not inflate the answer by counting every resolvable place as a completed planning practice.

5. **Are both models scientifically validated for every published use and state?** No. The sampled v0.44 loader is expressly inconclusive. Current known issues retain screening-only outputs, synthetic daily quantity versus AADT comparability, unknown model base year, unavailable use-specific acceptance, and borrowed ActivitySim coefficients at `KNOWN_ISSUES.md:11-12`. I did not inspect or rerun the full scientific chain and do not independently validate those diagnostics. Nothing sampled supports nationwide accuracy. Preserve each model, the common comparison boundary, rejected candidates, and untouched acceptance geography. Engine execution is not calibration, model agreement is not accuracy, and a better export is not a higher claim tier.

6. **What simple overlooked idea has the largest effect?** Make the record answer four ordinary questions everywhere: whose decision, about which place, under which rules, using which version of the evidence? Reuse existing Projects, Plans, work records, and evidence bundles to do it. The strongest immediate counterexample is the same consultancy preparing plans for different client governments. A single workspace state cannot answer that question. A second useful rule is to name what an export preserves and what reimport does before the planner downloads it.

7. **Which old rules or decisions are wrong now?** Workspace jurisdiction as legal authorization is wrong for cross-jurisdiction work. One California checklist for two plan kinds is wrong. Equating a round-trip label with record reconciliation is wrong. Closing a defect when only its disclosure or diagnosis shipped is wrong. Calling the desktop dependency free for government users is wrong. A universal mandatory designation layer deserves reassessment against amendment/review types. Keep the binding all-US v1 ambition, separate models, human control, source uncertainty, reusable modules, and self-service requirements. Do not resurrect closed model-execution problems from old notes, but also do not turn a closed diagnosis into a validated model.

8. **What should be joined, deepened, or removed before something new?** Join plan context to the project/evidence spine; deepen existing land-use production and implementation; connect the already written GeoPackage layer support; unify direct and governed evidence assembly; make workbook semantics explicit before adding safe reconciliation. Generic Plans currently consider six presence checks sufficient for readiness at `lib/plans/catalog.ts:111-177`, while Land Use Plans use versioned process records. Preserve both roles if planners need them, but distinguish linked-output completeness from statutory or decision readiness. Remove duplicate presentation and misleading completion labels when they fail to express a distinct job. Do not delete functioning modules or rewrite the database just to reduce the count. New development-review capability should first use Projects, plan relationships, and existing review controls; only a demonstrated ownership failure justifies a new top-level module.

9. **What would prove this recommendation wrong?** A current visible journey could falsify the authority finding by preparing a California plan for a California authority inside an Oregon consultancy workspace without changing workspace home or inventing geography, while refusing a genuinely mismatched California bundle. Plan-type-specific route evidence and an actual specific-plan artifact could falsify the shared-checklist finding. Actual production GeoPackages containing the exact linked model/designation features could falsify the export finding. A workbook reimport that updates the intended records with correct geography and review custody could falsify the narrow-round-trip finding. A current government-eligible free Docker Desktop license, or a proven free alternative already in the promised instructions, could falsify the installation finding. Repeated independent planners might show that housing/development depth blocks more important work than the proposed shared-record outcome; that would change sequencing, not remove those jobs from v1.

10. **What is the highest-leverage next completed outcome?** A planner working for a client agency can produce a plan-specific decision record, send it to a second person, receive and incorporate a requested change, approve the exact final version, and reuse its maps and tables outside OpenPlan. The record must carry the correct governing authority and rule version independent of workspace location, preserve source and model limitations, and create a named implementation action. Begin with California general and specific plans to expose different requirements, and a non-California or sovereign neutral case to prove the core does not assume California. This is a bounded extension of existing modules. It is not a nationwide completion claim, a new model calibration campaign, or permission to launch a large new implementation under the present review-only authorization.
