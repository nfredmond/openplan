## Proposed deployment and access design

Establish one reproducible production Linux reference deployment before multiplying provider recipes. Separate public web ingress from private database/admin/worker interfaces. Keep the web application responsive while resource-heavy jobs queue and run. Build-time public configuration, private credentials, artifact volumes, scheduler, mail, TLS and backup destinations form part of the release manifest. Use a pinned accepted release and staging checks; do not automatically expose every main push to a live demonstration.

Initially use invitation-based editable trial workspaces and an optional public read-only tour. The eventual fully working hosted outcome includes actual creation, data intake, analysis, engagement, reporting and background execution for the release's claimed capabilities. Invitations are a cost and privacy control, not a software paywall. Controlled trials can start before every v1 capability is complete, but each unfinished module and scientific limitation must remain visible and on the roadmap. Do not present a prerecorded result as a newly completed model run. Long calculations may continue after the presentation; users must be able to return in another browser and recover progress/results.

Use public or explicitly permitted demonstration material, with separate saved trial work per organization. A sample dataset's origin must be clear. No automatic reset may erase a visitor's saved work without an agreed disposable-data policy and warning. Real confidential agency data requires commissioned retention, access, incident and recovery practices; a demonstration account is not sufficient authority to hold it.

A visitor's ordinary browser cannot invoke Claude Code, Codex or OpenCode installed on a different computer. The no-install hosted demonstration needs configured server execution for its demonstrated agent path. Personal installed CLI use remains an optional authenticated device connection under A0, with scoped authority and the provider's actual allowed account mode. Do not pool Nathaniel's personal subscription across visitors, collect native login tokens or silently substitute paid API use. The browser-only baseline and the installed-device option must explain their requirements plainly.

## Trial-to-customer handoff and administration

Prefer customer-controlled hosting accounts, domain, billing and administrator ownership, with delegated support access. An implementation engagement supplies a verified installation, data migration, configuration, training, backup/restore and accepted workflow evidence. Annual administration supplies defined maintenance, update, backup verification, monitoring, access review and support windows. Customization has separately agreed outcomes, tests, migration/upgrade compatibility and maintenance ownership. Favor improvements in the shared main branch and configuration over indefinitely divergent client forks.

The exit path is a product requirement. Move an authorized customer's complete workspace into a separate installation without other customers' records. Preserve object bytes, geographic meaning, evidence and approval history, attachments, jobs and model artifacts; reconcile users/roles and reauthorize credentials safely. An ordinary report export cannot establish portability. After transfer, a customer administrator or replacement maintainer must sign in, continue a real job and restore a backup without Nathaniel. An annual service ending must not disable the software or trap the records.

Implementation pricing should follow measured commissioning effort; annual administration should follow a defined support/maintenance workload and explicit third-party costs. Do not invent a service price or promise unlimited enhancements, storage, model use or round-the-clock support. Community users retain usable documentation, releases, issues and PRs; free access does not promise that every requested feature will be built.
