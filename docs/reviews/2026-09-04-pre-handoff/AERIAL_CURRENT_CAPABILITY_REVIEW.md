## Trace 1: authored inputs to mission file

The mission detail page mounts the AOI and flight-plan sections at `openplan/src/app/(app)/aerial/missions/[missionId]/page.tsx:558-610`. The editor reads the saved plan and AOI, accepts camera, vertical intent, overlap, speed, gimbal pitch, margin and usable battery minutes, then calls `generateSurveyGrid` at `openplan/src/components/aerial/flight-plan-editor.tsx:433-453`. The reviewed result can be saved through the flight-plan PUT route. The export buttons at lines 891-919 call the three format variants of the export endpoint.

The generator derives photo footprints and spacing, selects an axis, clips passes and orders a serpentine with photo trigger points. It computes time as distance/speed plus an inter-pass turn allowance, then estimates battery count. See `openplan/src/lib/aerial/survey-grid.ts:462-555`. It discloses flat elevation, takeoff/ground-plane height, omitted transit time, and the straight-pass interpretation of curved corridors. Battery count does not partition the export into safe sorties or model return reserve. The exporter stops at each photo waypoint, whereas the duration estimate has no per-photo stop/capture-time term; it must not be represented as a complete flight-energy prediction.

The export route authenticates membership, reads mission AOI and saved parameters, recomputes their fingerprint, refuses missing/stale snapshots, parses the saved snapshot, and serves an attachment. See `openplan/src/app/api/aerial/missions/[missionId]/flight-plan/export/route.ts:75-242`. This protects against common accidental stale edits. It exports the saved grid rather than silently regenerating it at download time.

Actual file semantics in `openplan/src/lib/aerial/flight-exports.ts`:

- WPML uses namespace `http://www.dji.com/wpmz/1.0.2`; KMZ contains `wpmz/template.kml` and `wpmz/waylines.wpml`. The template currently contains author/timestamps/mission configuration, without a template Folder. Waylines use relative-to-start-point height, one waypoint/photo action per photo point, an optional first-waypoint gimbal action and stop/turn behavior. Mission configuration hardcodes return home and RC-loss behavior.
- The module deliberately omits `droneInfo` and `payloadInfo`. Its comment assumes Pilot 2 will bind the aircraft on import. That is an unverified compatibility claim, not evidence from a supported controller. The parallel DJI review should resolve required fields and model/firmware rules.
- `rth_altitude_m` is stored by the plan route but never supplied to the export builder. Changing that field does not change the file's return-height configuration. This is a concrete missing authored-setting-to-export connection.
- Litchi CSV carries one row/photo action per photo point. The UI warns above the code's 99-waypoint limit but still exports the unsplit file and tells the user to split it externally. No verified sortie splitting is implemented.
- Generic KML is deliberately 2D review geometry with stated height assumptions. It is not a flight-control file.

The legacy perimeter-based private JSON exporter is explicitly superseded in `openplan/src/lib/aerial/dji-export.ts`; its old API answers Gone. Do not count it as current DJI support.

### Mission integrity gaps

The PUT schema accepts `generatedPlan` as an arbitrary record at `openplan/src/app/api/aerial/missions/[missionId]/flight-plan/route.ts:83`. Lines 369-381 save it and stamp a fingerprint of the separately supplied parameters. The server does not establish that the snapshot was generated from those parameters or that its waypoints fit the AOI. The export parser performs structural/count checks, then uses snapshot altitude and speed. A caller with write access can therefore save a structurally valid, mismatched grid and receive a current fingerprint. This is a source-proven validation gap; it was not exercised live. The FNV fingerprint is documented as a staleness check, not a security hash.

The editor passes only the polygon's outer ring, at `flight-plan-editor.tsx:299,436`, and does not pass the generator's corridor object. Its parameter hash uses `corridorWidthM: null` at line 209. The pure corridor generator therefore must not be advertised as a full reachable corridor-planning workflow. Inner rings, no-fly exclusions, obstacle clearance, transit between disjoint clipped passes and terrain clearance need explicit validation. A grid with points inside the boundary is not proof that all connecting flight segments are safe. No physical flight-safety conclusion follows from this code review.

USB delivery is presently a downloaded file. No controller storage layout, transfer receipt, on-controller import verification, supported hardware/firmware matrix or saved-controller roundtrip was found. “Downloadable KMZ” and “DJI controller USB mission export works” must remain separate claims.

## Trace 2: source photos to held planning evidence

The imagery upload route checks membership, streams under a configurable default 64 MiB per-file ceiling, sniffs bytes, computes SHA-256, deduplicates, writes private storage and persists extracted EXIF fields. Explicit v1.1 signs the mission's stored photo objects and sends filename/size/checksum entries, with a default six-hour URL lifetime. See mission `process/route.ts:45-64,360-478`. Stored-photo read failure stops dispatch rather than falling back to an apparently empty mission. It records a job before calling the worker, at lines 519-545.
3. The worker authenticates and validates contract v1/v1.1, queues the request and returns accepted. `workers/odm_worker/intake.py` applies download/extraction size limits, zip-slip protection, filename sanitation, and declared size/hash checks for manifest photos. It then uploads images to NodeODM, commits a task and polls progress in `main.py:277-351`.

Custody downloads under limits, hashes bytes, stores private objects and records held/pending/failed/refused states. Raw signed URLs remain in the service-only callback record; member-readable descriptors redact them.
6. The mission page presents jobs, custody and private downloads. Its map renders a held PNG only when placement metadata is usable. `openplan/src/components/aerial/aerial-mission-map.tsx:1-28` explicitly defers measurement to external GIS using the GeoTIFF. ## Processing and evidence gaps that matter

**Recovery is not durable.** `workers/odm_worker/main.py:148-172` keeps jobs, queue and artifact registrations in memory. NodeODM task UUID exists only inside the running function. Restart loses reconciliation, retry identity and downloadable-link registration even when output files remain. The expiry sweep visits the in-memory artifact registry, so restart also loses knowledge needed to sweep older output directories. The supplied compose file has automatic restart but no durable job database or declared volume mounts and uses an unpinned NodeODM image. An automatic restart does not restore a job.

Callbacks retry three times and then log failure, in `workers/odm_worker/callbacks.py:18-70`; the pipeline marks its own job succeeded regardless of callback delivery. The app callback inserts the unique receipt before transition/custody. If later work fails, replay of the same callback ID returns `deduped` at `processing-callback/route.ts:123-149` without reapplying unfinished work. Terminal-state checks also use a previously read row, not an atomic transition. These seams need durable receipt/application states and recovery tests. The existing custody retry endpoint is useful, but it is not a complete job-transition/evidence-package recovery coordinator.

**Large output custody is still an HTTP/memory operation.** Defaults are 256 MiB per artifact and a 30-second custody budget in `openplan/src/lib/aerial/artifact-custody.ts:29-62`. The engine hashes streamed chunks but assembles bytes in memory before upload. Raising a ceiling does not create reliable multi-gigabyte resumable transfer. Worker source intake defaults to 40 GiB, while output archive extraction has no corresponding expansion ceiling in the inspected NodeODM client. Disk/resource admission, durable transfer, renewal/reconciliation before signed-link expiry and explicit NodeODM cleanup remain necessary for substantial jobs. Four waiting jobs and six-hour photo links are not a guarantee that imagery will remain readable when its turn arrives.

**Exact consumed inputs are not persistently recorded as a job manifest.** The app stores type/count/size and the preset, while the detailed request exists in the worker's in-memory job. The source-delete route explicitly acknowledges this and conservatively prevents deletion of any mission photo after any processing job exists, at `openplan/src/app/api/aerial/missions/[missionId]/imagery/[imageryId]/route.ts:117-153`. Preserve that protection. Add immutable per-job input IDs/hashes, source versions, engine/build/options and processing provenance before offering selective replacement or reproducible reruns.

**Accepted source formats diverge.** The imagery input advertises `.dng` at `aerial-imagery-panel.tsx:177`, and original filenames reach manifests. `workers/odm_worker/intake.py:23,119-127,249` collects only JPG/JPEG/PNG/TIF/TIFF extensions. A downloaded DNG is omitted; an all-DNG manifest fails, while mixed collections can process a subset. No conversion or explicit subset-acceptance step was found. This needs consistent intake capabilities and an exact consumed-photo count/hash manifest.

**A product name or artifact enum is not implemented analysis.** The local worker does not extract mesh files. No current aerial GCP/checkpoint management, RTK/PPK processing configuration, calibration review, accuracy report acceptance, point-cloud classification/editing, mesh/3D viewer, elevation profile, contours, area/distance/volume/cut-fill measurement, time-series surface comparison, thermal/multispectral processing or terrain-following mission workflow was found in the bounded inventory. Some may exist in upstream engines or older repositories; that is not an OpenPlan workflow. The parallel ODM comparison should establish the full target and reuse mapping.

**Network inputs need deployment-aware controls.** ZIP/manifest intake accepts HTTP(S), including local network addresses by design. Artifact custody follows redirects. This supports local Supabase, but a hosted multi-tenant deployment needs explicit trusted-origin/network rules and protection against redirect-based access to unrelated internal services. This review did not attempt exploitation or audit every network helper.
