# Preserve original aerial engine commands

NodeODM 2.2.4 repeats uploads as additional files and allows initialization to
replace draft metadata. The [native counterexample](../2026-10-11-odm-draft-reconciliation/STATUS.md)
shows that task absence does not establish absence of these effects.

This M3/M5b.2 candidate records commands without changing the deployed worker,
its public contract, engine default or scientific settings. It reuses the
private admission journal and retained-source readers, publication and lock.

## Original plan

Before recording a command, reverify the actual retained source pack through
its existing preparation API. Bind the immutable engine plan to the complete
original admission/authority context, exact source manifest hash, configured
engine instance, endpoint, API version, image digest, configuration hash and
credential reference. Store no credential value. Preserve one caller-supplied
canonical task UUID, explicit task name, ordered effective options and ordered
upload filenames. These are caller configuration, not live authority or engine
attestation.

The first candidate supports retained photo-manifest slots. It does not treat
a retained ZIP as an image. ZIP extraction needs its own exact derived-image
manifest and recovery proof before inclusion. File extensions do not establish
decoding or permitted imagery. The plan is independent of installation paths
so a verified relocated copy retains its original identity.

## Immutable effect records

Generate each command from that saved plan: initialization, each individual
upload and commit. Include stable method/path, original UUID header, explicit
form/options or multipart field, filename, source slot, size and hash. Record
the command and plan hash durably before returning the first-issue flag.
Exact repeats return false, including a request whose reply is missing.
Changed plan identity or saved command bytes refuse. A completed rename whose
directory sync raises also remains issued when next read. Preserve partial
records for diagnosis. Cooperative file locks exclude another local caller.

The flag records a first local intent. It is not live processing authorization,
proof of execution, authority, sequence readiness or verified engine custody.
The disconnected library issues no HTTP call. A future runtime adapter must
check those boundaries before transporting a newly recorded command. It must
not transport an existing uncertain command again.

Save a bounded exact response body and status after checking native success
shape and the original UUID where the API returns it. Preserve the original
raw JSON spelling and its hash, as well as the parsed value. Equal parsed JSON
with different raw bytes is a different reply and cannot overwrite the original.
Reject duplicate JSON keys, nonfinite numbers and invalid response types.
Record `engineCustodyVerification: unassessed` even for a success reply.
Failed or malformed responses leave the intent unresolved. Task info absence
and a supplied boolean cannot resolve it.

## Verification and limits

Test immutable plan/command/reply identity, private path handling, serialization,
actual retained-byte corruption, concurrent first issuance, interruption around
publication, response limits and restored-copy replay. Every changed test needs
a harmless survivor and a targeted broken behavior with its intended failure.
Keep a native process/root-copy trial separate from controlled publication
failures. Do not infer physical power-loss, live authority, actual engine
custody, image quality or full worker recovery from these checks.

Before connecting the runtime, add actual backend draft reconciliation under
owned engine identity and excluded writers, exact ZIP-derived image custody,
processing/commit recovery, complete output custody and terminal delivery.
Preserve the main merge hold and the relaunch owner's recorded exception.
