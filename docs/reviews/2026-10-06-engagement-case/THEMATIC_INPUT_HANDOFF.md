# Inspected context choices for thematic work

This checkpoint continues roadmap M9b from context-request commit `21b1f86a`.
It uses the existing thematic request, immutable contribution choice and worker
input preparation. It adds no module, model, execution grant or publication step.
The full contract and roadmap remain unchanged.

## Staff outcome and boundary

Before a theme request can prepare inputs, its author needs to select one complete
context result for every source contribution. The native choice operation already
reconstructs original context history and rejects a different source, parent,
contribution or incomplete result. This checkpoint exposes inspection and exact
choice retention through an authenticated HTTP boundary. The browser controls,
discovery of eligible contexts, browser command recovery and complete thematic
journey remain unfinished.

Inspection returns a bounded excerpt and identifies the original context request,
selection sequence, history manifest and final capture/result hashes. The command
also pins the thematic request's intent and binding hashes. The server reconstructs
the original context again and compares all inspected bytes before the native
write. It rechecks current thematic-request access before exposing private output.
An altered inspection remains a refusal; it cannot become a different saved choice.

The GET route also reads an existing choice under current staff access, including
an absent result. Only the thematic requester can propose a new choice. These
reads do not start work. POST uses native author custody, keeps exact replay status,
and grants no provider permission. Authenticated account/workspace headers and the
browser-origin check remain required. Unregistered assistant write markers receive
an executable refusal. Responses use `private, no-store`; raw context and choice
text do not enter audit logs. The request body is bounded to 8 KiB and inspection
to 30 seconds.

The browser verifier compares receipts with the exact inspected command before
any future recovery cleanup. It checks scope, author, request, contribution,
choice bytes and checksum. An excerpt marked truncated does not establish custody
of the unreturned full output. All generated wording stays `machine_unreviewed`.

## Evidence

The [verification record](thematic-inputs/verification.json) retains the source
hashes, focused checks and native outcomes. All 85 tests across three suites pass.
The existing server suite now includes inspection without a write, late access
loss, altered final request reads, exact pinned rejection and interrupted replay.
The HTTP suite exercises the real route with mocked identity/native functions.
The portable suite exercises actual parsing and Web Crypto checks.

A harmless comment control passes all three suites. Ten targeted faults fail for
the named inspected intent/binding/choice, late access, receipt bytes/author,
preview checksum, selection sequence, workspace-header or assistant-refusal
boundary. Source files are restored byte for byte. The runner is retained with
the evidence and accepts an application directory and fresh output directory.

The native probe uses the owned restore-target stack at API port 29821. It creates
one synthetic thematic request from an existing complete parent and inspects a
completed 13-frame context. Altered intent, thematic binding and exact choice
text are refused without changing native choice custody. The first valid save's
acknowledgement is deliberately withheld from the simulated caller. Exact retry
returns the same saved bytes with replay status. A native mutation that removes
the exact-choice comparison fails because the altered inspection is accepted.
Harmless and restored native runs pass. The probe's credentials and exact command
remain in the private recovery directory; only sanitized identities and hashes
are retained here.

This evidence does not establish native HTTP transport, browser storage recovery,
rendering, keyboard/console behavior, complete input membership or sealing,
provider execution, semantic correctness, practitioner acceptance or release
readiness. The thematic request has one selected contribution; it is not a complete
theme workflow. Build and GitHub outcomes follow as separately identified checks.
