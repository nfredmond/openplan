# Keep a supplied aerial task reply and reopen its recorded facts

Run this local command from the repository root. It does not contact NodeODM.
It stores supplied reply bytes, then prints a digest and bounded reported facts.
It does not verify where the supplied reply came from or whether it is current.

The engine root must contain the original private `plan.json` generated by the
existing engine-custody helpers. The metadata root must already exist privately,
outside the engine root. Neither root can contain the other. A missing root is
not automatically commissioned. Do not place metadata inside the engine command
journal; that journal deliberately rejects unrelated files.

For a fresh metadata root, create the directory explicitly with mode 0700.
Use absolute paths. Keep the supplied reply in a private directory and an owned
mode-0600 file, with no symlink or hard-link aliases. Supply the original response
status explicitly. A non-200 status or unsupported reply refuses.

```sh
python3 -B workers/odm_worker/task_observation_cli.py \
  --engine-root /absolute/private-engine-root \
  --records-root /absolute/private-task-metadata-root \
  --record-file /absolute/private-replies/task-info.json \
  --response-status 200
```

Keep the returned `bodySha256`. Read that exact reply later, including after
restoring both selected roots:

```sh
python3 -B workers/odm_worker/task_observation_cli.py \
  --engine-root /absolute/restored-private-engine-root \
  --records-root /absolute/restored-private-task-metadata-root \
  --read-digest <bodySha256>
```

The default command deadline is two seconds. `--timeout` supplies a positive,
finite local deadline covering the input read and record operation. File reads
are local; this does not supervise a network poll or guarantee interruption of
blocked kernel filesystem I/O. Replies are limited to 1 MiB. Record and source
plan bounds also remain enforced by the existing helpers.

Equal replay keeps the original record. Different raw reply spellings receive
different digests. A lost plan in a populated metadata root refuses. Record
status, image count and progress remain reported facts; unavailable counts stay
unknown. The summary omits raw reply bytes, error detail and engine configuration.
Assessment fields remain `unassessed`, and transport/publication remain denied.

Register and capture both selected roots in the installation's existing recovery
inventory. The command itself does not discover roots or stop their writers.
Quiesce applicable writers before an operator-declared root capture. Preserve the
original protected point and use new runtime copies when reopening.

This command does not poll or process a task, reconcile an uncertain effect,
adopt a new engine, deliver a callback or approve a result. It cannot establish
actor access, image quality, complete installation recovery or useful long jobs.
The [dated verification record](../../docs/reviews/2026-10-13-odm-task-observation-cli/STATUS.md)
keeps the actual command and native evidence limits.

The [known-root inventory check](../../docs/reviews/2026-10-13-odm-metadata-inventory/STATUS.md)
exercises the existing installation inventory and root-set capture with both
required roots. It preserves the distinction between a successful selected-root
capture and complete installation recovery.
